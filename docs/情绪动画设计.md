# 立绘情绪动画设计（素材片段播放器）

> 状态：**设计稿，未实现**。本文只描述方案、要改的文件、验收标准，不含代码改动。
> 目标版本：0.4.0（版本号统一用 `node scripts/version.mjs <版本> --write` 改，不要手抄）
> 涉及模块：`render`（逐帧渲染）、`resource`（素材 CRUD）、`plot`（记录级特效）、前端 `record` + `ResourceManager`

---

## 0. 一句话结论

情绪动画 = **可导入的帧序列片段（clip）+ 一个播放器**，而不是在软件里写动画引擎。

- 美术在 AE（或任何能出动画的软件）里做好，导出 **PNG 序列（带 alpha）**；
- 软件只负责四件事：**在哪（锚点）、第几帧、放多大、放多久**；
- **GIF 是允许的输入格式，但不是内部存储格式**——GIF 只有 256 色 + 1bit alpha，叠在立绘/渐变背景上必然出现硬边锯齿与色带，所以导入时就解码成 PNG 帧，之后再也不碰 GIF。

---

## 1. 为什么不是"软件内动画引擎"

### 1.1 两条路线的成本对比

| | 内置动画引擎（用代码画） | 素材片段播放器（本方案） |
|---|---|---|
| 做一个"花飞出" | 要写粒子系统 + 花朵绘制 + 动画曲线，且每个动画都要写一遍代码 | AE 里做完导出 60 张 PNG，软件里零代码 |
| 做一个"怒气符号旋转缩放" | 相对便宜（30 行左右），但符号本身还得画 | 同上，素材是什么就是什么 |
| 画面质量上限 | 取决于代码画得多细，除非你写一个绘图库 | 取决于美术，不设上限 |
| 编辑器实时预览 | 要么在 TS 里把同一个动画**再实现一遍**，要么编辑时看不见 | 直接播放同一批帧图，天然一致 |
| 分辨率 | 矢量清晰（优势） | 素材放大后会软（对策见 2.3） |
| 用户自己换素材 | 不可能 | 换素材 = 换文件夹 |

### 1.2 这个项目里的三条硬约束

这三条不是空谈，是现有代码决定的：

1. **渲染已经是"静态层只画一次 + 逐帧叠变化的内容"**。
   `RenderOfVideo.exportRecordVideoStreaming` 先把背景/立绘/UI 底板合成一张静态层
   （`RenderOfVideo.java:152`），然后逐帧只画打字机文字（`RenderOfVideo.java:174`），文字没变就复用上一帧
   （`RenderOfVideo.java:194` 的"定格复用"）。播放器只需要"每帧贴一张已解码的图"；动画引擎则要在这条复用逻辑里
   插入时间轴求值，改造成本和出错面都大得多。

2. **编辑器预览是后端渲染的一张 PNG**（`RecordController.java:382`，前端 `RecordPreview.tsx:93`）。
   只有当"素材 = 一张张帧图"时，前端才能拿**同一批帧**在预览图上叠一层实时动画
   （`/assets/**` 已经静态映射好，`WebMvcConfig.java:54`）。如果是 Java 里的程序化引擎，预览要么
   在 TS 里重写一遍（每个动画写两遍），要么编辑时根本看不见动画。

3. **锚点是现成的**。立绘的裁剪方框 `(faceX, faceY, length)` + `posX/posY` + 缩放已经能推出"脸框中心在画面里的位置"
   （`CharacterVisual.java:113`），情绪特效能**自动贴在角色头上**，不需要手摆坐标。推导见附录 B。

### 1.3 关于 GIF 与 AE（回答两个具体疑问）

**GIF 当内部格式会毁画质，当输入格式没问题。**

- GIF 调色板只有 256 色：立绘发丝、渐变背景上会出现色带；
- GIF 的透明是 1bit（要么全透要么全不透）：叠在立绘上，边缘会出现一圈硬锯齿，放大到 1080p 后很明显；
- GIF 的帧延迟以 10ms 为单位且各家写法不一，时间轴不可信。

所以：**接受 GIF/APNG/WebP/MP4/WebM 作为输入 → 导入时用 FFmpeg 解码成帧 → 以 PNG 序列落盘**。
解码链路是现成的（`WebpImageDecoder.java:114` 那套 `AV_PIX_FMT_BGRA` 保住 alpha 的写法直接复用，
本机实测 FFmpeg 6 带 `gif` / `apng` / `webp` / `webp_anim` / `vp9` 解码器）。

**AE 不需要"导出参数"。**
要做的事情只有一步：`渲染队列 → 输出模块 → 格式 PNG 序列 + 通道 RGB+Alpha`，2 秒 30fps 就是 60 张 PNG。
不用导出关键帧、不用写脚本、不用管"参数"。

"导出参数"的那套东西叫 **Bodymovin（Lottie）**：AE 插件把动画导成 JSON 关键帧，播放器按参数实时渲染。
它确实能"改颜色/改速度"，但 **Java 侧没有成熟的 Lottie 渲染器**（官方只有 Web/Android/iOS），
接进来只能走 JNI/rlottie，成本远大于收益。真要做"可调色"的动画，在 Java 侧对帧做整体着色的成本要低得多（P2）。

### 1.4 明确不做（v1）

- 不做时间轴 / 关键帧编辑器（那是另一个软件）；
- 不做 Lottie；
- 不做程序化逐帧绘制（P2 再做，且**烘焙成帧**后复用同一个播放器，不引入第二条渲染路径）；
- 不把动画烘焙进预览 PNG（理由见 6.1）。

## 2. 素材规范

### 2.1 目录结构

```
{dataRoot}/assets/emotion/<clipId>/
├── clip.json          # 元数据（可缺省，见 2.2）
└── frames/
    ├── 0001.png
    ├── 0002.png
    └── ...
```

`{dataRoot}` 由 `RuntimePaths` 决定：安装版是 `%APPDATA%\limbus-company-plot-video-generator`，
开发/测试是 `demo/`（见 `RuntimePaths.java` 与 pom 里的 `-Dlbc.data.dir`）。
**不要**用仓库里的 `demo/assets`，那是测试数据。

设计上故意做成"一个素材一个文件夹"：用户把 AE 导出的 60 张 PNG 丢进 `frames/` 就能用，
不需要开软件、不需要进数据库。

### 2.2 clip.json

```json
{
  "id": "happy_flower_a1b2c3d4",
  "name": "开心-花开",
  "fps": 30,
  "frameCount": 60,
  "width": 600,
  "height": 600,
  "emotions": ["happy"],
  "playback": "once",
  "anchorX": 0.5,
  "anchorY": 0.5
}
```

| 字段 | 缺省 | 说明 |
|---|---|---|
| `id` | 目录名 | 目录名是唯一权威；JSON 里写了也不作为主键 |
| `name` | 目录名 | 界面显示名 |
| `fps` | 30 | 落盘帧率，导入时统一重采样到 30 |
| `frameCount` | `frames/` 里 PNG 个数 | 与实际不符时以实际为准并告警 |
| `width` / `height` | 读取第 1 帧 | 画布尺寸，用于算绘制大小 |
| `emotions` | `[]` | 绑定哪几种标准情绪（`Emotion.java` 的 8 种小写 code：`normal/happy/angry/sad/surprised/confused/blush/hurt`） |
| `playback` | `"once"` | `once` 播完消失 / `loop` 循环 / `hold` 播完停在最后一帧 |
| `anchorX`/`anchorY` | 0.5 | 素材内的锚点（相对画布，0~1）。美术把主体放在画布中心时不用改 |

**缺 clip.json 时**：目录名当 id、`name`、`fps=30`、`emotions=[]`、`frames/*.png` 按文件名排序。
这保证"手放素材"这条路能跑通；情绪绑定可以在界面上补。

### 2.3 出图规格

| 项 | 建议值 | 原因 |
|---|---|---|
| 画布边长 | 1080p 下目标显示尺寸的 **2 倍** | 4K 导出时素材会被放大（例：显示 300px → 出 600px） |
| 帧率 | 30 | 与视频一致，导入时不会产生重复帧抖动 |
| 时长 | 0.5 ~ 3 秒 | 记录本身最短也有 `DEFAULT_STAY_FRAMES`=75 帧（2.5 秒，见 `RecordDurationCalculator`），太短会"一闪而过" |
| 帧数上限 | 300 帧（10 秒） | 导入时硬性拒绝，防呆 |
| 通道 | **必须带 alpha**，不要黑底/白底 | 否则叠上去是一块不透明方块 |
| 主体位置 | 画布中心 | 锚点默认在画布中心 |

### 2.4 体积预算

- 单帧 600×600 带 alpha 的 PNG ≈ 150~350KB；
- 60 帧 ≈ 10~20MB；**建议起步用 400×400 / 30 帧（≈3~5MB）**；
- 帧图走 `ImageCache`（默认预算 192MB，`ImageCache.java:50`）：400×400×4B×60 ≈ 38MB，单素材完全放得下；
  同时开多个素材时由 LRU 自动淘汰，不需要另造缓存。

### 2.5 id 与 URL

- `id` 必须匹配 `^[A-Za-z0-9_-]{1,64}$`（目录名，同时也是 URL 段）；
- 帧 URL：`/assets/emotion/<id>/frames/0001.png`（`/assets/**` 已映射，缓存 3600 秒）；
- **重新导入生成新 id**（追加 8 位随机后缀）：`/assets/**` 有 1 小时浏览器缓存，复用旧 id 会让前端播到上一版帧。

## 3. 数据模型

### 3.1 扩展现有的 `EffectVisual`

记录级特效目前只有三种起始转场（`EffectVisual.java`），新增一种类型即可复用现有链路
（`record.effects` 已经随记录一起序列化、随导出请求发给后端）：

```json
{
  "type": "EMOTION_ANIM",
  "enabled": true,
  "mode": "auto",
  "clipId": null,
  "targetIndex": -1,
  "offsetX": 0,
  "offsetY": 0,
  "scale": 1.0,
  "playback": null,
  "delayFrames": 0
}
```

| 字段 | 缺省 | 说明 |
|---|---|---|
| `type` | — | 固定 `"EMOTION_ANIM"` |
| `mode` | `"auto"` | `auto` 按情绪自动选素材；`fixed` 用 `clipId` |
| `clipId` | null | `mode=fixed` 时指定素材 |
| `targetIndex` | -1 | `-1` = 说话人；否则取 `record.chars` 中该下标（与 `CharactersProperties` 的列表顺序一致） |
| `offsetX/offsetY` | 0 | 相对锚点的偏移，**1080p 设计画布像素**（编辑器里对着预览拖出来的直观值） |
| `scale` | 1.0 | 素材原始像素 → **场景**像素的比例。剧情模式下场景还要缩到 0.8（见 5.2），所以 `1.0` 时 600px 的素材在成片上约占 480px 宽 |
| `playback` | null | 覆盖素材自身的播放模式；空 = 用素材的 |
| `delayFrames` | 0 | 第几帧开始播（给"说完一句才冒花"留的口子，v1 不做 UI） |

**兼容性**：`EffectVisual` 与 `Record` 都标了 `@JsonIgnoreProperties(ignoreUnknown = true)`，
旧工程里没有这个类型 → 渲染端什么都找不到 → 不画。反过来，旧版本软件打开新工程会忽略这个特效，
不会崩。字段全部有缺省值，不需要数据库迁移。

### 3.2 触发优先级

渲染时按这个顺序决定"播哪个 clip"：

1. `mode=fixed` 且 `clipId` 有效 → 用它；
2. 目标立绘的 **`portrait.emotion`** 命中某个 clip 的 `emotions` → 用它；
3. 台词的 `dialogue.emotion` 命中 → 用它（只有文本解析器会写这个字段，见下）；
4. 都没有 → 不播。

**为什么以立绘情绪为主信号**：编辑器里选立绘时会连带选中它带的情绪
（`CharactersProperties.tsx:647` 的立绘选择弹窗，情绪在 `PortraitSettings.tsx:39` 里维护），
用户只要上传"罗佳-开心"立绘并在记录里选它，动画就会自动出现，**不需要任何新 UI**。
而 `dialogue.emotion` 目前只有 `PlainTextRecordsParser` 会写，编辑器里**没有入口**
（`RecordEditor.tsx:185` 新建记录时恒为 `NORMAL`），所以它只能作为兜底。

> 想让它成为主信号的代价：在"文本"属性页加一个情绪下拉（复用 `emotionMapper.ts`），属 P2。

**歧义处理**：多个 clip 绑了同一种情绪时，取 `id` 字典序第一个，并在资源管理页给出提示。

### 3.3 与起始转场共存

两者互不影响：转场是"整屏叠一层再淡出"（`StartTransition.apply` 在帧合成**之后**就地改写像素），
动画是"在帧上再画一个 sprite"。顺序上转场会盖住动画前 20 帧（`StartTransition.FRAMES = 20`），
这是符合预期的——转场本来就是画面切换。

## 4. 导入管线

### 4.1 支持的输入

| 输入 | 处理 |
|---|---|
| `.gif` / `.apng` / `.webp`（动图）/ `.mp4` / `.webm` / `.mov` | FFmpeg 逐帧解码 |
| `.png` 多选 / `.zip`（内含 PNG 序列） | 按文件名排序读帧，跳过解码 |
| 手工放 `frames/` 目录 | 不经过接口，直接可用 |

### 4.2 解码

用 `FFmpegFrameGrabber` + `grabber.setPixelFormat(avutil.AV_PIX_FMT_BGRA)`，逐帧 `grabImage()`。
**不要**用 `Java2DFrameConverter` 直接转（`WebpImageDecoder.java` 的类注释里记了它把 BGRA 当 ARGB 读的坑，
会导致 alpha 全丢、整体发红）。BGRA 字节序 → 自己组装 `TYPE_INT_ARGB` 的写法照抄
`WebpImageDecoder.decodeWebpData`。

每帧同时记录时间戳（`frame.timestamp`，微秒），供重采样用。

### 4.3 重采样到 30fps

源素材可能是 24fps、12fps（GIF）、可变帧率（MP4），统一按时间轴重采样：

```
源帧: [(t0, img0), (t1, img1), ..., (tn, imgn)]
末帧时长: tN + (tN - tN-1)        # 最后一帧的显示时长，缺失时按 1/25 秒
输出帧数: ceil(总时长 * 30)，上限 300
第 k 帧: 取"时间戳 <= k/30 秒"的最后一个源帧（等价最近邻前向采样）
```

- GIF 的 10ms 时间片在这一步被抹平；
- 源帧率低于 30 时会产生重复帧（每个源帧占多帧），这是正确的"定格"，不会抖动；
- 源帧率高于 30 时丢帧，运动仍然连续。

### 4.4 校验（不通过就整体拒绝，不落半成品）

- 解出 0 帧 / 全部帧解码失败 → 报"这个文件解不出画面"；
- 帧数 > 300 → 报"超过 10 秒上限"；
- 单边 > 4096 或非正方形以外的异常尺寸 → 拒绝（超大帧会撞 `ImageCache` 预算）；
- 各帧尺寸不一致（GIF 允许多帧不同尺寸）→ 统一贴到"最大宽×最大高"的透明画布左上角；
- 目录 id 非法 → 自动生成，不报错。

### 4.5 落盘与失败处理

```
assets/emotion/.importing-<uuid>/     # 先写临时目录
        → 校验通过 → 原子改名成 assets/emotion/<id>/
        → 任一步失败 → 删除临时目录，返回明确错误
```

理由和预览图缓存写盘一样（`RecordController.writeCacheAtomically`）：直接写目标目录，
中途失败会在资源库里留下半个素材，而扫描逻辑只看目录存在，那个坏素材会被一直列出来。

## 5. 渲染

### 5.1 锚点

**关键结论：脸框中心与"立绘用户缩放"无关，只由身高和偏移决定。**（推导见附录 B）

场景空间（`plot` 模式的 0.8 缩放**之前**）：

```
HEAD_HALF = DEFAULT_CHARACTER_HEAD_LENGTH / 2 = 91.5
faceCenter.x = 960 + portrait.adjX + chara.adjX + HEAD_HALF
faceCenter.y = DEFAULT_CHARACTER_HEIGHT_Pixels
             + (DEFAULT_CHARACTER_HEIGHT - character.height) * Pixels_per_centimeter
             + portrait.adjY + chara.adjY + HEAD_HALF
             = 221 + (171 - height) * 12 + adjY 合计 + 91.5
```

三种锚点模式（`anchorX/anchorY` 之外再加一层语义，v1 只做前两个）：

| 模式 | 位置 | 用途 |
|---|---|---|
| `face`（默认） | 脸框中心 | 汗滴、怒气符号、腮红 |
| `head` | 脸框上边缘（`faceCenter.y - HEAD_HALF`） | 花瓣从上往下飘、问号/惊叹号 |
| `canvas` | 画面中心 (960, 540) | 整屏闪白、全屏粒子 |

### 5.2 剧情模式的 0.8 变换（**最容易踩的坑**）

`plot=true` 时，场景是在 1080p 设计画布上**先合成为一张图、再缩到 0.8、偏移 (192,108)** 才叠 UI 的
（`RenderOfImage.java:275`，`PLOT_SCENE_SCALE = 0.8`，`RenderOfImage.java:51`）。
所以锚点必须跟着变换，否则动画会贴到左上方：

```
designAnchor.x = 192 + faceCenter.x * 0.8 + offsetX
designAnchor.y = 108 + faceCenter.y * 0.8 + offsetY
```

**并且**：立绘本身在场景里，所以素材的绘制尺寸也要乘 0.8：

```
drawW = clip.width  * effect.scale * portraitUserScale * 0.8
drawH = clip.height * effect.scale * portraitUserScale * 0.8
drawX = designAnchor.x - drawW * anchorX      # anchorX=0.5 → 居中
drawY = designAnchor.y - drawH * anchorY
```

`portraitUserScale` = `CharacterVisual.getRenderScale() / (DEFAULT_CHARACTER_HEAD_LENGTH / portrait.length)`，
即用户手动缩放（1.0 = 未缩放）。让特效跟着立绘一起放大，否则用户把立绘拉大 2 倍后特效会显得很小。
（`CharacterVisual` 目前只暴露 `getRenderScale()`，需要补一个 `getUserScale()`。）

**输出到帧**（帧是 `width×height` 的输出分辨率，不是 1080p）：

```
frameX = designX * frameWidth / 1920
frameY = designY * frameHeight / 1080
frameW = drawW  * frameWidth / 1920
```

### 5.3 逐帧接入点

改 `RenderOfVideo.exportRecordVideoStreaming`（`RenderOfVideo.java:174` 的循环）：

```java
// 循环外，一次性算好（纯算术，不读图）
List<EmotionPlacement> placements = EmotionAnimation.placementsFor(record, plot, width, height, frameRate);
boolean hasAnimation = !placements.isEmpty();

// 循环内
if (hasAnimation) {
    // 有动画：每帧都不一样，必须现画一份，不能进"定格复用"
    frame = frameTexts != null
            ? renderSingleFrame(staticBackground, frameTexts[frameIndex], record.getDialogue(), width, height)
            : copyImage(staticBackground);
    EmotionAnimation.draw(frame, placements, frameIndex);   // 画在最上层
    // 转场叠在动画之上，保持"整屏过渡"的语义
} else if (...) { /* 原逻辑不动 */ }
```

**与"定格复用"的关系**：有动画的记录放弃复用（`reusableFrame` 那条分支），
因为每帧画面都不同。代价见 5.5。

**绘制顺序**：`静态层 → 台词 → 动画`（动画在最上层）。
台词在下方对话框里、动画在头部，正常不重叠；而"整屏闪白/爆发"这类素材本来就该压在 UI 之上。
如果想要"动画在台词之下"，给 `renderSingleFrame` 加一个绘制回调即可（P2）。

**统一质量设置**：绘制时套 `RenderQualityUtils.setupHighQualityRendering(g)` +
`VALUE_INTERPOLATION_BICUBIC`，和现有图层一致。

### 5.4 分层导出

v1 只在 `FULL` 分层出动画，其余分层（`UI_ONLY` / `BG_CHARACTERS` / `BACKGROUND_ONLY` / `CHARACTERS_ONLY`）不画。

- 理由：分层导出的消费方是自己合成，如果每层都画会叠多份；
- 局限：只用分层合成的用户看不到特效。后续可加一个 `VFX_ONLY` 分层专门出动画（P2）；
- 文档/UI 上要写明这一点。

### 5.5 性能预算

| 项 | 量级 | 说明 |
|---|---|---|
| 每帧 `copyImage(1080p)` | ~2~3ms | 有动画的帧本来就要重新合成 |
| 每帧贴 1~2 个 sprite | <0.5ms | 双三次缩放 600→600 基本是 memcpy |
| 帧图解码 | 首次 ~5ms/帧，之后命中 `ImageCache` | 60 帧首帧总代价 ~300ms，可接受 |
| 失去"定格复用"的内存开销 | 无 | 复用只是省时间，不省内存 |

一段 5 秒的记录（150 帧）大约多花 0.5 秒，相对整条视频的编码时间可以忽略。

### 5.6 非剧情模式

`plot=false`（人格故事）时**立绘根本不画**（`RenderOfImage.java:265` 与 `:299` 都是 `if (plot) renderCharacters(...)`），
所以没有锚点，`placementsFor` 直接返回空列表。这条要写进注释，避免后人以为是 bug。

## 6. 编辑器实时预览

### 6.1 为什么不把动画烘焙进预览 PNG

- 预览 PNG 有磁盘缓存（`PREVIEW_CACHE_VERSION = "v10"`，`RecordController.java:90`），烘焙动画就要改缓存键，
  而且每次请求只能看到同一帧，**看不到动画**；
- 前端要"实时看到动画"，只能靠浏览器自己播；
- 所以：**预览 PNG 保持干净（不含动画），前端在图片上叠一层 canvas 播放器**。

### 6.2 placement 接口：坐标只在 Java 里算一次

新增 `POST /api/records/animation-placement`，请求体和 `/records/preview` 一样（`Record` + `plot` + 宽高），
返回**归一化**坐标，前端只按百分比摆放，不做任何换算：

```json
{
  "items": [
    {
      "clipId": "happy_flower_a1b2c3d4",
      "frameBaseUrl": "/assets/emotion/happy_flower_a1b2c3d4/frames/",
      "frameCount": 60,
      "fps": 30,
      "playback": "once",
      "delayFrames": 0,
      "x": 0.53, "y": 0.33, "w": 0.25, "h": 0.25
    }
  ]
}
```

`x/y` 是**左上角**、`w/h` 是**尺寸**，全部除以 1920/1080。
预览图 = 设计画布整幅缩放到请求尺寸（`composeFinalImage`），所以归一化坐标在任何显示尺寸下都对得上，
不需要前端重算锚点，也不会出现"预览和成片位置不一样"。

> 用百分比而不是像素，是为了让预览图在编辑器里怎么拉伸都不漂。

### 6.3 前端播放器

新增 `features/record/EmotionAnimationOverlay.tsx`（约 100 行）：

```
1. 拿 record + plot + videoWidth/videoHeight → 请求 placement（record 视觉摘要变化时才重取）
2. 预加载 frameBaseUrl + 0001..NNNN.png（new Image()），全部 onload 后开播
3. requestAnimationFrame：elapsed = now - startTime；
   localFrame = floor(elapsed/1000 * fps) - delayFrames
   once:  localFrame 越界 → 停止（画布清空）
   loop:  localFrame % frameCount
   hold:  min(localFrame, frameCount-1)
4. <canvas> 绝对定位覆盖在预览 <img> 上，内部尺寸 = 显示尺寸 × devicePixelRatio
   只在 sprite 区域 clearRect + drawImage，其它区域保持透明
```

挂在 `RecordPreview.tsx` 的 `.preview-image` 容器里（和 `<img className="preview-render">` 同级）。
`RecordPreview` 已经在维护"视觉摘要"（`RecordPreview.tsx:39`），动画相关的字段变化会自然触发重取。

### 6.4 资源管理页试播

同一套播放器组件复用到新 tab（见 8.2）：列表里点素材 → 在原地循环播放 → 用来确认"画布中心对准了没有、
尺寸合不合适"。

## 附录 A：AE 导出 PNG 序列的步骤

1. 新建合成，尺寸按 2.3（例：600×600），帧率 30，时长 2 秒；
2. 画动画，**主体放在画布中心**，背景保持透明（不要加纯色层）；
3. `合成 → 添加到渲染队列`；
4. 输出模块 → 格式选 **PNG 序列**，通道选 **RGB + Alpha**，其它默认；
5. 输出路径指向一个空文件夹 → 渲染 → 得到 `xxx_00000.png … xxx_00059.png`；
6. 把整个文件夹改名成素材 id（如 `happy_flower_a1b2c3d4`），放进
   `%APPDATA%\limbus-company-plot-video-generator\assets\emotion\<id>\frames\`；
   或在资源管理页的"情绪动画"里把这几张 PNG 选上导入。

> AE 的 PNG 序列命名自带补零，按文件名排序即时间顺序，不需要重命名。
> 如果导出的是带黑底的 MP4，也能导入，但透明区域会变成不透明黑块——所以一定要 PNG 序列。

## 附录 B：锚点公式推导

由 `CharacterVisual.updatePos()`（`CharacterVisual.java:113`）：

```
baseScale   = DEFAULT_CHARACTER_HEAD_LENGTH / portrait.length   // 183 / length
renderScale = baseScale * userScale                             // userScale 默认 1
anchorX     = VIDEO_WIDTH/2 + portrait.adjX + chara.adjX
anchorY     = DEFAULT_CHARACTER_HEIGHT_Pixels
            + (DEFAULT_CHARACTER_HEIGHT - chara.height) * Pixels_per_centimeter
            + portrait.adjY + chara.adjY
posX        = anchorX + (length/2)*baseScale - (faceX + length/2)*renderScale
posY        = anchorY + (length/2)*baseScale - (faceY + length/2)*renderScale
```

脸框（`faceX, faceY, length, length`）在画面上的中心：

```
centerX = posX + faceX*renderScale + (length/2)*renderScale
        = anchorX + (length/2)*baseScale - (faceX + length/2)*renderScale
          + faceX*renderScale + (length/2)*renderScale
        = anchorX + (length/2)*baseScale          // renderScale 项全部抵消
        = anchorX + 91.5                          // (length/2)*(183/length) = 91.5
```

同理 `centerY = anchorY + 91.5`。

**结论**：脸框中心 = 固定偏移 + 91.5，**与 `faceX/faceY/length` 和用户缩放都无关**。
这也意味着：用户把立绘放大缩小时，情绪动画的锚点不会漂——只要按 5.2 把尺寸乘上 `userScale` 即可。

## 附录 C：关键伪代码

**解析目标与素材**

```java
List<EmotionPlacement> placementsFor(Record record, boolean plot, int frameW, int frameH, int fps) {
    if (!plot) return List.of();                     // 非剧情模式没有立绘
    EffectVisual fx = firstEnabled(record.getEffects(), EffectVisual.TYPE_EMOTION_ANIM);
    if (fx == null) return List.of();

    CharacterVisual target = resolveTarget(record, fx);   // targetIndex>=0 ? chars[i] : 说话人
    if (target == null || target.getPortrait() == null) return List.of();

    EmotionClip clip = repository.resolve(fx, target, record.getDialogue());  // 见 3.2
    if (clip == null) return List.of();

    Anchor a = anchorOf(target, clip, fx);           // 见 5.1 / 5.2，返回设计画布坐标
    double w = clip.getWidth()  * fx.getScale() * target.getUserScale() * PLOT_SCENE_SCALE;
    double h = clip.getHeight() * fx.getScale() * target.getUserScale() * PLOT_SCENE_SCALE;
    double x = a.x - w * clip.getAnchorX() + fx.getOffsetX();
    double y = a.y - h * clip.getAnchorY() + fx.getOffsetY();

    // 归一化：前端按百分比摆放；视频端再乘输出分辨率
    return List.of(new EmotionPlacement(clip, x / 1920, y / 1080, w / 1920, h / 1080,
                                        fx.getDelayFrames(), pickPlayback(fx, clip)));
}
```

**逐帧绘制**

```java
void draw(BufferedImage frame, List<EmotionPlacement> list, int frameIndex) {
    Graphics2D g = frame.createGraphics();
    try {
        RenderQualityUtils.setupHighQualityRendering(g);
        g.setRenderingHint(KEY_INTERPOLATION, VALUE_INTERPOLATION_BICUBIC);
        for (EmotionPlacement p : list) {
            int local = p.localFrame(frameIndex);     // delayFrames 之后才开始，once 播完返回 -1
            if (local < 0) continue;
            BufferedImage img = p.clip().frameAt(local);   // 内部走 ImageCache
            if (img == null) continue;
            g.drawImage(img,
                (int) Math.round(p.x() * frame.getWidth()),
                (int) Math.round(p.y() * frame.getHeight()),
                (int) Math.round(p.w() * frame.getWidth()),
                (int) Math.round(p.h() * frame.getHeight()), null);
        }
    } finally {
        g.dispose();
    }
}
```
