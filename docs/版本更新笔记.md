
## 0.2.3

- 修复安装版「立绘显示为红色『加载失败』方块」的问题。日志里只有一句
  `NoClassDefFoundError: Could not initialize class org.bytedeco.ffmpeg.global.avutil`，
  真实根因被 JVM 的类初始化失败缓存掩盖了。实际原因有两个，都会让 WebP 立绘变成红块：
  - **通道顺序**：FFmpeg 抓帧拿到的是 BGRA，旧代码交给 JavaCV 的 `Java2DFrameConverter` 转换，
    它按通道数猜类型、把 BGRA 当成 ARGB 读，于是 alpha=255 的不透明像素变成"红 + alpha≈8"，
    整张立绘呈半透明红块。现在由 `WebpImageDecoder` 按 BGRA 字节序自己组装 ARGB。
  - **原生库**：安装版走 Spring Boot 可执行 jar，原生库 jar 嵌在 `BOOT-INF/lib/` 里，
    JavaCPP 必须先把 DLL 释放到缓存目录才能 `System.load`；这条链路一断，它不会报"找不到 DLL"，
    而是退化成 `System.loadLibrary("jniavutil")`，最终以
    `UnsatisfiedLinkError: no jniavutil in java.library.path` 收场。
    现在由 `NativeLibraryBootstrap` 在启动时固定 JavaCPP 缓存目录并预热，成功/失败都有完整日志。
  - 这类故障**本地永远复现不了**：`mvn spring-boot:run` / IDE 用扁平 classpath，
    原生 jar 是磁盘上的真实文件，只有 `java -jar` 才会暴露。
  - `pom.xml` 里原先加的 `<requiresUnpack>` 实测在 spring-boot-maven-plugin 3.2.0 上
    对带 classifier 的原生包不生效（打出来的 jar 里没有任何解包标记），已移除并把原因写进注释。
- 新增安装包自检：`java -jar demo-<版本>-SNAPSHOT.jar --self-check=webp`
  不启动 Spring、不连数据库，现场解码一张内联的最小 WebP 并校验 alpha 与通道顺序，
  通过返回 0、失败返回 1。日志里会打印 `JavaCV 原生库来路`（能直接看出是嵌套 jar 还是扁平 classpath）、
  JavaCPP 缓存目录与 ffmpeg/ffprobe 实际路径，是"立绘变红"最快的排查入口。
- 立绘读不出来时的报错不再是一句"读不出来"：`ImageReader` 会带上具体失败原因
  （原生库不可用 / 文件损坏 / 路径不存在），日志里也能直接搜到。
- 版本号现在会显示在界面上与日志里（同一真源，界面/日志都没有硬编码版本号）：
  - 设置 → 关于 新增「版本 x.y.z」，经 IPC 取 `app.getVersion()`
  - 前端日志启动时打印「应用版本: x.y.z | 运行模式: 开发/安装版」
  - 后端启动日志打印「后端版本: x.y.z」，`GET /api/health` 也返回 `version`
- 统一版本号来源：版本号只在 `demo/frontend/electron-react-app/package.json` 的 `version` 里维护，用 `node scripts/version.mjs <x.y.z> --write` 一次性同步到 `demo/pom.xml`、`application.yml` 的 `app.version` 和 `package-lock.json`
- 修正历史遗留的版本号不一致：此前 `package.json` 一直停在 0.1.0（安装包文件名与"关于"里显示的版本都落后于实际发版），后端 `pom.xml` 停在 `1.0-SNAPSHOT`；现在两者都是 0.2.3（后端 jar 为 `demo-0.2.3-SNAPSHOT.jar`）
- CI 发版前会校验 tag 版本与 `package.json` 版本一致，不一致直接失败，避免再发出文件名与版本号对不上的安装包
- 新增 `node scripts/version.mjs`（查看/修改/校验版本号）与 `node scripts/version.test.mjs`（版本工具自测）
