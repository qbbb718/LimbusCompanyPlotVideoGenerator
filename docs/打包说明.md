## 打包分发

### Github Action打包


顺序固定为：**① 改版本号 → ② commit + push main → ③ 有旧 tag 先删 → ④ 打 tag 并核对它指的 commit → ⑤ push tag**。

#### 1. 改版本号（只动源码，不碰 tag）

```powershell
# 查看当前版本、以及各处版本号是否一致
node scripts\version.mjs
# 改成 0.6.1（不带 --write 只是干跑，打印会改哪些行）
node scripts\version.mjs 0.6.1 --write
# 只校验不改（CI 用的就是这个）：比对各处是否一致
node scripts\version.mjs --check
# 版本工具自测（改过 scripts\version.mjs 后跑一次）
node scripts\version.test.mjs
```

顺手在 [版本更新笔记](版本更新笔记.md) 顶部加一节 `## 0.6.1`，那是发版说明的来源。

#### 2. 提交，tag 必须打在这笔提交上

```powershell
git add -A
git commit -m "0.6.1"
git push origin main
```

工作区有未提交的改动时 `git tag` 照样能成功，但 tag 里不含那些改动 —— 所以必须先 commit。

#### 3. 同名 tag 先删干净（重复发版时最容易踩的坑）

`git tag v0.6.1` 遇到同名 tag 会 `fatal: tag 'v0.6.1' already exists` 直接失败，
而紧接着的 `git push` 不会因此停下：推上去的还是**旧 tag → 旧 commit（旧版本号）**，
CI 就停在开头那串 `[FAIL]` 上。所以先查、先删：

```powershell
git tag --list v0.6.1             # 有输出说明本地已有，需要删
git tag -d v0.6.1                 # 删本地 tag
git push origin :refs/tags/v0.6.1 # 删远端 tag（GitHub Releases 里那次失败的 release 一并删掉）
```

#### 4. 打 tag，并核对它指的 commit

```powershell
git tag v0.6.1
git rev-parse HEAD               # 当前提交
git rev-list -n 1 v0.6.1         # tag 指向的提交：必须与上一行完全一致
# 再从 tag 内容里读一次版本号：必须是 0.6.1，这一步最能提前发现「tag 打早了」
git show v0.6.1:demo/frontend/electron-react-app/package.json | Select-String '"version"'
# CI 的那条校验命令，本地也能跑
node scripts\version.mjs --check-tag v0.6.1
```

> 注意 `--check-tag` 比的是**工作区里的文件** + 「git 里有这个 tag」，它不读 tag 里的内容，
> 所以 tag 打早了它照样打印 `OK`（工作区是 0.6.1，tag 也真的存在）。能抓住「tag 打早了」的
> 只有上面那两行哈希对比（`rev-parse HEAD` vs `rev-list -n 1 v0.6.1`）和
> `git show v0.6.1:<路径>`——本地全绿、CI 却报 `version: 0.3.3`，就是这种情况。

#### 5. 推送

```powershell
git push origin main v0.6.1
```

只有推 tag 才触发 CI，只推 `main` 不会发版。跑完 GitHub Releases 里会有
`LCP0.6.1.exe`、`*.blockmap` 和 `latest.yml`（自动更新用）。

#### tag 已经推到旧 commit 了怎么救

不用重做版本号，把 tag 挪到正确提交上、强推覆盖远端即可，CI 会重新跑一次：

```powershell
git tag -f v0.6.1 HEAD           # 或 git tag -f v0.6.1 <正确的 commit>
git push origin v0.6.1 --force   # 覆盖远端同名 tag；只影响这个 tag，不动 main
```

#### 常见报错对照

| 报错 | 原因 | 处理 |
| --- | --- | --- |
| `version: 0.3.3 (expected 0.6.1)` + 一串 `[FAIL]` | tag 指到改版本号之前的 commit | 按上一条把 tag 挪到正确提交并强推 |
| `fatal: tag 'v0.6.1' already exists` | 本地已有同名 tag，这次 `git tag` 没生效 | 先 `git tag -d` + 删远端 tag，再重打 |
| `[rejected] v0.6.1 ... (already exists)` | 远端已有同名 tag 且指向别的 commit | 确认要覆盖：`git push origin v0.6.1 --force` |
| `git tag v0.6.1 does not exist` | 只推了 `main`，tag 没推 | `git push origin v0.6.1` |
| 本地 `--check` 通过但 CI 失败 | 版本号改动没 commit，或 commit 了没推 `main` | 先 commit + `git push origin main` |
| `npm ci` 报 `Missing: ... from lock file` 或刷 `EBADENGINE` | CI 的 Node/npm 版本与锁文件不匹配 | 见下面「`npm ci` 报锁文件不同步」 |

（`workflow_dispatch` 手动 Run workflow 只把校验换成 `--check`，后面的构建和 `--publish always`
照旧执行，所以「只想验版本号」还是在本地跑 `node scripts\version.mjs --check` 更快。）

#### `npm ci` 报锁文件不同步（0.6.0 发版失败）

```
npm error `npm ci` can only install packages when your package.json and package-lock.json
          or npm-shrinkwrap.json are in sync.
npm error Missing: yaml@2.9.1 from lock file
```

两个原因叠在一起：CI 当时用 Node 18（自带 npm 10），锁文件却是在 npm 11 上生成的。npm 11 会省略
`tailwindcss → postcss-load-config` 那条**可选 peer** `yaml@2` 的锁条目，npm 10 的 `npm ci` 却把它
当成「锁文件缺条目」直接判红；同时 `@testing-library/jest-dom@6.10`（`node >= 22`）和
`brace-expansion@5`（`20 || >= 22`）在 Node 18 上只会刷 `EBADENGINE` 警告。

现在的配置：`release.yml` 固定 `node-version: "22"` + `npm install --global npm@11`（与生成锁文件的
npm 大版本一致），`package-lock.json` 里也补上了 `node_modules/tailwindcss/node_modules/yaml@2.9.1`，
所以 npm 10 / npm 11 都能通过。改过依赖之后，本地先跑一遍：

```powershell
cd demo\frontend\electron-react-app
npm install          # 更新 package-lock.json
npm ci --dry-run     # 不删 node_modules，但会像 CI 一样先校验锁文件
```

# 本地打包说明

日常本地出安装包，只要跑一个脚本：

```bat
E:\LimbusCompanyPlotVideoGenerator\demo\build-package.bat
```

双击运行，或在 cmd / PowerShell 里执行都可以（脚本自己会把 demo 当成工作目录，不用先 `cd`）。

## 产物在哪

| 内容 | 路径 |
|---|---|
| 安装包 | `E:\LimbusCompanyPlotVideoGenerator\release\LCP<版本号>.exe`（版本号见 `package.json` 的 `version`，查看：`node scripts/version.mjs`） |
| 增量更新校验文件 | `E:\LimbusCompanyPlotVideoGenerator\release\...exe.blockmap`、`latest.yml` |
| 免安装的解包目录（可直接跑） | `E:\LimbusCompanyPlotVideoGenerator\release\win-unpacked\` |
| 构建日志 | `E:\LimbusCompanyPlotVideoGenerator\demo\logs\build-<时间戳>.txt` |

产物目录由 `PACK_OUTPUT` 决定，脚本里已设为仓库根目录的 `release\`（绝对路径），并通过
`npx electron-builder … -c.directories.output="%PACK_OUTPUT%"` 传给 electron-builder。
想临时换位置，可以在调用前自己设：

```bat
set PACK_OUTPUT=D:/build-out
demo\build-package.bat
```

GitHub Actions 不经过这个脚本，`electron-builder.yml` 里的 `output: release` 保持默认，
产物仍落在 `demo/frontend/electron-react-app/release`，与 `.github/workflows/release.yml`
上传产物的路径一致 —— 改本地输出目录不影响 CI 发版。（如果以后让 CI 直接调用这个脚本，
要注意脚本会用 `-c.directories.output` 覆盖 yml 的输出目录，上传路径需要相应调整。）

## 脚本做哪几步

0. （打包前）把素材与初始库组装成打包载荷 `demo\pack\`：`demo\assets` + `demo\data`，本地打包时再把开发机上新建的**角色 / 序列帧动画 / `project.db`** 叠上去（见下面「本地开发素材随包发布」）。失败就停在这一步，`release\` 不会被改名
1. 用 jlink 生成内置 JRE（`demo\jre\`，已存在则跳过）
2. `mvn clean package -DskipTests` 打后端 jar（`demo\target\demo-<版本号>-SNAPSHOT.jar`）
3. `npm run build` 打前端（`demo\frontend\electron-react-app\build\`）
4. 打包**两次**，各出一份安装包（见下面「两个安装包：完整版 / 精简版」）：
   - 4a. 用完整载荷打 `LCP<版本号>.exe`，打完立刻逐文件校验安装包里的素材；
   - 4b. 把载荷重建成精简版（`pack-assets.mjs --lite`），再打 `LCP<版本号>-lite.exe`，校验它**没有**多余的素材；
   - 4c. 最后把载荷重建成完整版，`demo\pack\` 不会停在精简状态。
   打包前会先准备 winCodeSign 缓存、并打印实际使用的下载镜像。

打包前请**先关掉正在运行的程序**，并让编辑器放开对这个目录的占用，否则 `release\win-unpacked\resources\app.asar` 被占用会导致第 4 步失败（占用源与处理见下面注意事项）。

## 两个安装包：完整版 / 精简版

每次打包（本地 `build-package.bat` 和 CI 的 release.yml）都出两份，文件名只差一个后缀：

| | 完整版 | 精简版 |
|---|---|---|
| 文件名 | `LCP<版本号>.exe` | `LCP<版本号>-lite.exe` |
| `resources\assets` | 全部素材：`ui` / `effects` / `fonts` / `characters` / `backgrounds` / `audios` / `animation-clips` / `thumbnails`（含本地开发出来的角色与序列帧动画） | **只有 `ui` / `effects` / `fonts`**（预览与导出跑起来的最低要求） |
| `resources\data` | `project.db`（+`-wal`）、`records.json` | **没有**：首次启动由后端自动建空库 |
| 体积 | 约 320 MB（只有仓库里的 `demo\assets` 时）～ 800 MB+（带上本机全部角色立绘时，取决于角色数量） | **264 MB**（实测；大头是后端 jar + 内置 JRE + Electron，素材只占 40 MB） |
| 适合谁 | 想开箱即用、不想自己导入素材的用户 | 只要软件本身，素材自己导入的用户 |
| 自动更新 | —— | **`latest.yml` 指向这一份** |

为什么更新走精简版：更新只是换程序，素材早在用户自己的数据目录（`%APPDATA%\limbus-company-plot-video-generator\assets`）里，覆盖安装不会删、也不会改；下载 264 MB 比下载 800 MB 现实得多。反过来，装了精简版的用户以后从 Releases 换成完整版也没问题（同一个程序，只是随包多带了素材）。

维护注意：

- **精简版必须最后打**。两次 electron-builder 都会写 `latest.yml`，最后一个写的才算数；顺序反了自动更新就会去下 800 MB 的完整版。
- 精简版的文件名靠命令行覆盖：`npx electron-builder --win --x64 -c.nsis.artifactName="LCP${version}-lite.${ext}"`。**不要**改 `electron-builder.yml` 里的 `nsis.artifactName`（完整版还要用原来的名字）。在 PowerShell 里这条参数必须用单引号，否则 `${version}` 会被当成变量展开成空串、打出 `LCP-lite.exe` 这种名字（实测踩过）。
- 两个版本共用同一个 `demo\pack`：打完完整版 → 重建成精简版 → 打精简版。electron-builder 每次都会重建 `win-unpacked`（实测：完整版打完里面有 characters，精简版打完只剩 ui/effects/fonts），所以两个版本不会互相污染；本地脚本还会在第二次打包前主动删掉 `win-unpacked`（顺手释放几百 MB）。
- 每次打包完都会跑 `scripts\verify-packaged-assets.ps1`：完整版核对"载荷里的每个文件都在包里"，精简版额外断言 `resources\assets` 下**没有** `characters` / `animation-clips` / `backgrounds` / `audios` / `thumbnails`、`resources\data` 是空的 —— 精简版悄悄带上全套素材是这次最容易出的错。
- 只想要其中一个、手动打包：

  ```powershell
  cd demo\frontend\electron-react-app
  node ..\..\scripts\pack-assets.mjs                       # 完整载荷
  npx electron-builder --win --x64                         # 完整版

  node ..\..\scripts\pack-assets.mjs --lite                # 精简载荷
  npx electron-builder --win --x64 '-c.nsis.artifactName=LCP${version}-lite.${ext}'   # 精简版
  ```

  打完记得再跑一次 `node ..\..\scripts\pack-assets.mjs` 把 `demo\pack` 恢复成完整版。

## 安装包文件名与安装路径提示

两处都集中在 `demo\frontend\electron-react-app\electron-builder.yml`：

| 需求 | 配置 | 结果 |
|---|---|---|
| 安装包文件名 = LCP + 版本号 | `nsis.artifactName: "LCP${version}.${ext}"` | `release\LCP0.6.1.exe`（`latest.yml`/`.blockmap` 也自动跟着改名，自动更新不受影响） |
| 精简版文件名 = LCP + 版本号 + `-lite` | 命令行 `-c.nsis.artifactName="LCP${version}-lite.${ext}"`（不进 yml） | `release\LCP0.6.1-lite.exe` |
| 选择安装位置页加“安装路径中不能有中文或空格”提示 | `build\installer.nsh`（electron-builder 的 `nsis.include` 默认路径） | 提示里的“中文”“空格”加粗、字号加大（普通 9pt / 加粗 13pt） |

`build\installer.nsh` 做的事：**替换 MUI 内置的目录页**，改用一个同样带“目标文件夹”分组框、路径输入框、浏览按钮的自定义页面，只是多出那行提示。之所以要整页替换：内置目录页没有可挂的页面回调（`MUI_PAGE_CUSTOMFUNCTION_*` 会先被“安装模式”页用掉），而 NSIS 3.04 没有 `SetTimer`，StdUtils 的定时器回调里又调不了 System 插件，没法事后往上贴控件。替换后的行为与内置页保持一致：`--updated` 自动更新时跳过本页、路径末尾自动补 `LimbusCompanyPlotVideoGenerator`、空路径会拦下提示。

几个维护注意点：

- **`build\installer.nsh` 必须保存成 UTF-8 with BOM**：makensis 靠 BOM 判断源码是 UTF-8，没有 BOM 时中文会按系统 ANSI 代码页（GBK）解析成乱码，安装界面上就是一堆问号。
- 文件里只用 `$R0-$R9`（大写）做 System::Call 的返回值中转：System 插件里 `r0` 指 `$0`、`R0` 指 `$R0`，大小写混用会静默取到空值。
- 文字宽度用 `DrawText` + `DT_CALCRECT` 量，不要改成 `GetTextExtentPoint32W`：后者在 System 插件里调不通（调用会中断当前页面函数）。
- 只有在 `allowToChangeInstallationDirectory: true` 时才会接管目录页；关掉该配置时这个 include 什么都不做。

## 本地开发素材随包发布（`demo\pack`）

### 为什么要有这一步

本地开发（`start_all.bat` / `mvn spring-boot:run`）时，程序把**新建的角色、序列帧动画、工程库**写到数据根目录：

| 内容 | 本地路径 |
|---|---|
| 角色立绘 | `%APPDATA%\limbus-company-plot-video-generator\assets\characters\<角色ID>\` |
| 序列帧动画 | `...\assets\animation-clips\<ID>\`（`clip.json` + `frames\*.png`） |
| 工程库 | `...\data\project.db`（有可能还有 `project.db-wal`） |

而打包源是仓库里另外两份：`demo\assets`（随包发布的素材）、`demo\data`（初始库）。两边**不会自动同步**：以前在资源管理里新建了角色、导入了序列帧动画，只要没手动拷进 `demo\assets`，打出来的安装包里就没有它们 —— 用户装上后「角色列表空空的、序列帧动画一套都没有」，而开发机上一切正常。

现在打包前会跑一次 `scripts\pack-assets.mjs`，把两边合并成**打包载荷** `demo\pack\`（不进 git）：

```
demo\pack\
├── assets\        = demo\assets  + 数据根目录的 characters / animation-clips / thumbnails
├── data\          = demo\data    + 数据根目录的 project.db（连同 -wal）、records.json
└── manifest.json  # 这一包到底带了什么：数据根目录、条目 ID、文件数、体积
```

`electron-builder.yml` 只从 `demo\pack\assets` / `demo\pack\data` 打包，所以安装目录里 `resources\assets`、`resources\data` 就是合并后的内容；安装版首次启动仍按原逻辑把缺失素材补进用户数据目录，用户开箱即用。

> 为什么不让 electron-builder 挂两条 `extraResources`（一条 `demo\assets`、一条本地素材）自己合并：**同 `to` 的多条映射是并发拷贝的**（`copyFiles` 对 matcher 做 map），两边有同一相对路径时谁后写完全看运气。实测同一份文件（200 KB 与 900 KB 两份）连跑 5 次有 1 次留下的是旧的那份 —— 那就是"这次打出来的包 `project.db` 是旧的、立绘是旧的"这种查不出来的问题。合并必须在打包前用脚本顺序做掉。

### 常用命令

```powershell
# 手动重新生成载荷（打包脚本会自动跑，一般不单独执行）
node scripts\pack-assets.mjs

# 只看会打什么，不动磁盘
node scripts\pack-assets.mjs --dry-run

# 数据目录不在默认位置（例如设置页把「资源存储位置」改到了 D:\SOFTWARE\LCP）
node scripts\pack-assets.mjs --data-root "D:\SOFTWARE\LCP"

# 不带本地项目库（避免把自己的剧情记录发给用户）
node scripts\pack-assets.mjs --no-database

# 顺便把本地的背景 / 音频也带上（默认不带，见下表）
node scripts\pack-assets.mjs --assets characters,animation-clips,thumbnails,backgrounds,audios

# 精简版载荷：只有 ui/effects/fonts，不带任何角色/背景/音频/动画，也不带数据库
node scripts\pack-assets.mjs --lite
```

- 数据目录优先级：`--data-root` > 环境变量 `LBC_DATA_DIR` > 默认 `%APPDATA%\limbus-company-plot-video-generator`。
  **不读 `data-location.json`**：那个定位文件只有安装版的主进程会用，`mvn spring-boot:run` 起的后端根本不看它，本地开发时数据永远落在默认目录。脚本发现定位文件指向别处时只会打一行提示（"我的素材明明在那儿却没进包"多半就是它）。
- 每次都**整目录重建** `demo\pack`：在资源管理里删掉的角色不会从旧载荷里复活，被 checkpoint 掉的 `-wal` 也不会残留。
- `demo\pack\` 只是打包输入（`.gitignore` 已忽略），随时可以整个删掉，下次打包会重建；删掉之后**别直接**跑 `npx electron-builder`，否则安装包里会没有素材。
- 想跳过载荷重建：打包前 `set LCP_PACK_ASSETS=off` —— 它会**连精简版一起跳过**（精简版必须先把载荷重建成精简状态），只按 `demo\pack` 现状打一个完整版。只适合复现某个旧状态，别用它发版。
- 自测：`node scripts\pack-assets.test.mjs`（CI 的版本校验步骤里也会跑）。

### 默认带哪些、不带哪些

下表是**完整版**的口径；精简版（`--lite`）一律只带 `ui` / `effects` / `fonts`，其余全部不带、也**不读数据目录**（详见上面「两个安装包」）。

| 数据根目录下的 | 完整版默认 | 说明 |
|---|---|---|
| `assets\characters` | ✅ | 角色立绘。同名角色以本地开发的那份为准；`01李箱` 这类中文目录照旧保留，不会被覆盖掉 |
| `assets\animation-clips` | ✅ | 序列帧动画。**没有数据库**，目录本身就是全部内容 |
| `assets\thumbnails` | ✅ | 立绘缩略图，只有几十 KB |
| `data\project.db`（+`-wal`） | ✅ | **角色列表来自数据库**：只带图片不带库，新装用户看不到角色条目 |
| `data\records.json` | 有就带 | 旧格式的剧情记录 |
| `assets\backgrounds`、`assets\audios` 等 | ❌ | 仍用 `demo\assets` 里的；要带就加 `--assets ...`（会顺带把你的开发素材发出去） |

> ⚠️ **完整版会明显变大**：带的是本机全部角色立绘（当前 1850 个文件、约 540 MB），安装包会从 ~320 MB 涨到 800 MB 量级。不打算发布的角色，先在「资源管理 → 角色」里删掉再打包；只想给用户程序本身的，让 ta 下精简版。

> **升级安装不会改用户已有的库**：`resources\data` 与 `resources\assets` 只在用户数据目录的 `data\`/`assets\` 不存在时整份复制（`electron.js` 的 `ensureUserDataFiles`），之后启动只补**缺失**的素材文件、不覆盖已有文件。所以这批随包发布的角色与动画是"新装用户开箱即用"；对已经用了一段时间的老用户，要给他们补一批角色还得走「资源管理 → 导入全部资源」（导出这台机器的资源包再让他导入）。

### 校验与 CI

- 校验集中在 `scripts\verify-packaged-assets.ps1`，两种阶段 × 两个 profile 各跑一次：
  - `-Stage payload`（打包**前**）：载荷本身是否可用。`demo/pack` 缺失时 electron-builder 只打一行 `file source doesn't exist` 警告，照样能出安装包，所以必须自己拦。
  - `-Stage package`（打包**后**）：完整版核对"`demo\pack` 里的每个文件都在安装包里"，并打印 `characters: N, animation clips: M`；精简版额外断言包里**没有** `characters` / `animation-clips` / `backgrounds` / `audios` / `thumbnails`、`resources\data` 是空的。
  - 任一检查失败就 `BUILD FAILED`，并保留上一份产物（`release.old` 不会被删）。
- **CI（release.yml）跑的是同一套脚本、同样的顺序**（完整载荷 → 完整版 → 校验 → 精简载荷 → 精简版 → 校验），只是没有本地开发数据，完整版等于"只有 `demo/assets` + `demo/data`"的产物。

### 排查：素材没进包

| 现象 | 先看什么 |
|---|---|
| 汇总行 `characters: 0` | 数据目录指错了。看脚本第一行 `Local data root (...)`；装过正式版的话定位文件可能指向别处，用 `--data-root` 指过去 |
| `[INFO] data-location.json points at ...` | 提示，不是错误：本次用的是默认目录，定位文件指向的是安装版的数据目录 |
| 角色有、序列帧动画没有 | 确认 `assets\animation-clips` 下确有 `<ID>\clip.json`；只有 `frames` 没有 `clip.json` 的目录对程序来说不是一套动画 |
| 新装用户看不到角色 | 用了 `--no-database`，或 `project.db` 里本来就没有这些角色 —— 角色条目在数据库里，不在目录里 |
| `[ERROR] ... is not a SQLite database` | 数据目录里的 `project.db` 不是 SQLite 库（拷错了/被别的程序占着）。脚本拒绝打包，而不是打一个坏库出去 |
| 想看这一包到底带了什么 | `demo\pack\manifest.json`：数据根目录、每类素材的文件数与体积、角色/动画 ID 列表 |

## 注意事项

- **安装目录名必须不带空格**：安装目录与可执行文件名由 `electron-builder.yml` 里的 `win.executableName` 决定（当前是 `LimbusCompanyPlotVideoGenerator`），不要为了"好看"把它改回带空格的 `productName`。安装路径带空格时，Spring Boot 3.2 生成的嵌套 jar URL（`jar:nested:/.../BOOT-INF/lib/xxx.jar!/...`）会把这个空格原样带进去，JavaCV/JavaCPP 解析该 URL 时抛 `URISyntaxException`，导致 FFmpeg 原生库加载失败（`UnsatisfiedLinkError`）；它是 `Error`，不会被 `catch (Exception)` 捕获，表现就是**安装版"导出视频"进度永远停在 0%**，且没有任何报错弹窗。本地 `mvn spring-boot:run` 用的是扁平 classpath，不会触发这个坑，所以本地永远看不出问题。`productName`（界面显示名、卸载项名称）、`nsis.shortcutName` 都不受 `executableName` 影响；安装包文件名由 `nsis.artifactName`（`LCP${version}.${ext}`）单独指定，与 `executableName` 无关。
- **装过带空格目录的旧版本，不建议"卸载再装"**：安装器会把上一次的安装目录写进注册表（`HKCU\Software\<APP_GUID>\InstallLocation`）并在升级时沿用，直接覆盖安装会装回原来带空格的目录，修复不生效；而卸载又会因为 `deleteAppDataOnUninstall: true` 删掉 `%APPDATA%\limbus-company-plot-video-generator`（项目数据库、assets、resources 都在里面，删了就没了）。推荐做法：运行新安装包，在"选择安装位置"页把路径改成不带空格的目录（例如 `...\Programs\LimbusCompanyPlotVideoGenerator`），装完再把旧的带空格目录手动删掉。另外要求整条安装路径都不带空格：如果 Windows 用户名本身带空格（例如 `C:\Users\John Doe`），`%LOCALAPPDATA%\Programs\...` 依旧带空格，这种情况只能靠把 Spring Boot 升到 ≥ 3.2.3 从根上解决。
- **需要管理员权限**：目前 `demo` 目录树里没有当前用户的权限条目（只有继承来的 Administrators/SYSTEM/Authenticated Users/Users），普通权限下脚本会卡在写 `demo\logs\build-*.txt` 并打印 `Access is denied.`，但外层仍显示 `BUILD SUCCEEDED`，很容易误判。所以请用**管理员身份**运行 cmd / PowerShell 再执行脚本。
- 想一次性修好权限，在管理员 PowerShell 里执行（把 `<你的用户名>` 换成实际账号）：
  ```powershell
  icacls "E:\LimbusCompanyPlotVideoGenerator" /grant "<你的用户名>:(OI)(CI)F" /T /C /Q
  ```
  之后再普通权限打包即可。
- **打包脚本会校验安装包内的素材**（校验逻辑在 `scripts\verify-packaged-assets.ps1`，本地和 CI 用的是同一份）：两次打包各自跑一遍，检查 `release\win-unpacked\resources\assets` 是否存在，以及 `ui\`（border_1080p/dialogBox/speaker-camp/speaker-name/location）、`fonts\ChineseFont.ttf`、非空的 `effects\` 是否都在；缺任何一个就直接 `BUILD FAILED`，并且**保留上一份产物**（`release.old` 不会被删），避免发出一个"预览/导出必坏"的安装包。
  - `effects\` 的非空判定是**递归**的：情绪气泡素材落在子目录里（`effects\speech_bubble\...`），非递归地数顶层文件永远得到 0，会把一份完好的产物误判成"effects folder is empty"（2026-11-11 那次打包失败就是这个原因）。
  - 对照的源是 **`demo\pack\`**（打包载荷，含本地开发素材），不是 `demo\assets`：脚本会把 `demo\pack\assets` 下的每个文件按相对路径到 `resources\assets` 里逐个找一遍，少任何一个都会报 `packaged assets are incomplete: N of M files from the payload were not packaged` 并列前 5 个；`demo\pack\data` 里的每个文件（`project.db`、`project.db-wal`、`records.json`）也必须在 `resources\data` 里，否则报 `packaged data is incomplete`。这条是给 `extraResources` 配置写错、素材被静默漏打的兜底：素材名里带 `[]` 之类通配字符、大小写不一致都不会影响判定（用 `-LiteralPath` + 小写相对路径表比对）。
  - 汇总行 `assets ok (full): ... characters: N, animation clips: M, ...` 里的两个数字就是角色与序列帧动画的**进包数量**，改过 `electron-builder.yml` 之后先看它们。
  - 精简版还会额外断言包里**没有** `characters` / `animation-clips` / `backgrounds` / `audios` / `thumbnails`、`resources\data` 为空，否则报 `lite package must not carry optional assets`。
  - 打包**前**还有一次"载荷体检"（`-Stage payload`）：`demo\pack` 缺失时 electron-builder 只会警告 `file source doesn't exist`、照样能打出安装包，所以脚本提前拦一次，失败时 `release\` 都还没被动过。
  - CI（release.yml）不走 `.bat`，但跑的是同样的四个校验步骤（完整载荷 → 完整版 → 精简载荷 → 精简版）。
- **素材缺失可以自愈/手动修复**：安装版后端每次启动都会用 `-Dapp.assets.bundled=<安装目录>\resources\assets`（由 `public/electron.js` 传入）和用户数据目录下的 `assets` 做一次逐文件比对，只补缺失或 0 字节的文件，已存在的一律保留（用户自己上传/替换的素材不会被覆盖，也不会删除任何文件）。用户也可以在"设置 → 素材自检与修复"里点「从安装包补齐缺失素材」手动补一次。
- 脚本只会停掉**仓库内**的残留进程（java/javaw/electron/app-builder/打包出的程序本身），不再像以前那样 `taskkill /im java.exe` 无差别杀掉机器上所有 Java 进程（那会顺带杀掉 VS Code 的 Java 语言服务器等无关程序）。构建期间如果控制台闪一下黑屏属正常现象。
- 脚本不会先删旧产物，而是把上一份 `PACK_OUTPUT` 改名成 `release.old` 再打包：**打包成功**才删掉它，**打包失败**（或目录被占用）时它原样保留，所以一次失败的构建不会把你的旧安装包弄没。只有目录名恰好是 `release` 时才会改名，把 `PACK_OUTPUT` 指到别的目录名（例如 `D:/build-out`）会跳过这一步、并在日志里给出 `[WARN]`。
- **目录被占用会直接失败退出**，不会再让 electron-builder 抛一堆 Go 堆栈，也不会删掉任何东西：日志里会写 `[ERROR] Cannot move ... aside - a file inside it is still locked by another process. Nothing was deleted`。日志里紧接着会提示占用源；也可以直接 `set PACK_OUTPUT=<另一个目录>` 再跑一次绕开它。
- **最常见的占用源是编辑器，不是程序本身**：2026-10-05 那次 `release\win-unpacked\resources\app.asar` 被占用，实测是 VS Code 的文件监视进程（`Code.exe --type=utility --utility-sub-type=node.mojom.NodeService`）一直握着这个 200+MB 的文件。已在 `.vscode\settings.json` 里把 `release`/`target`/`jre`/`node_modules` 加进 `files.watcherExclude` 与 `search.exclude`；如果改完设置仍被占用，**重载 VS Code 窗口**（`Ctrl+Shift+P` → `Developer: Reload Window`）或直接关掉 VS Code 再打包。想确认到底是谁占着，用「资源监视器」→ CPU → 关联的句柄里搜 `app.asar`。
- 非 CI 模式下脚本只在最外层暂停一次（内层的输出被重定向进日志，所以内层不暂停）；以前那种“构建完成后控制台卡住、要盲按一下键”的现象已修掉。
- 想让脚本按 CI 模式跑（不暂停、打包带 `--publish never`），设 `CI=true` 或 `CI=1`；设成 `CI=false` 不会进入 CI 模式。
- **脚本必须保持纯 ASCII（注释写英文）**：内层会执行 `chcp 65001`，此时 cmd 解析多字节（中文）注释会错位，把注释行的后半截当成命令执行，日志里就会出现 `'xxx' is not recognized as an internal or external command`。中文说明一律写在本文档里，不要写进 `.bat`。
- 另外修掉了一个会让“打包成功也报失败”的坑：旧版失败分支写成 `if errorlevel 1 ( ... echo ... (try rebooting) ... goto :FATAL )`，echo 文本里的 `)` 会被 cmd 当成括号块结束，导致 if 体提前结束、后面的 `goto :FATAL` 无条件执行。现在每次打包后用 `if not errorlevel 1 goto :FULL_PACKED`（精简版是 `:LITE_PACKED`）分流。

## 打包时下载失败（GitHub 连不上）

第 4 步（electron-builder）打包时还要额外下三样东西，默认全部来自 `github.com`：

| 下载项 | 大小 | 谁在下 | 默认地址 |
|---|---|---|---|
| Electron 本体 `electron-v39.8.10-win32-x64.zip` | 137 MB | app-builder | `github.com/electron/electron/releases/...` |
| NSIS 工具链 `nsis-3.0.6.1`、`nsis-resources-3.4.1` | 数 MB | app-builder-lib | `github.com/electron-userland/electron-builder-binaries/...` |
| `winCodeSign-2.6.0`（内含 rcedit、signtool） | 5.6 MB | app-builder | 同上 |

国内网络经常连不上。2026-10-18 那两次本地打包就是死在这里——后端 jar、前端 `build/` 都成功了，只有第 4 步失败：

```
  • packaging       platform=win32 arch=x64 electron=39.8.10 appOutDir=...\release\win-unpacked
  ⨯ Get "https://github.com/electron/electron/releases/download/v39.8.10/electron-v39.8.10-win32-x64.zip":
    read tcp 192.168.1.7:10141->20.205.243.166:443: wsarecv: A connection attempt failed ...
  ⨯ ...\app-builder.exe process failed ERR_ELECTRON_BUILDER_CANNOT_EXECUTE
```

现在脚本在调用 electron-builder 之前就把镜像变量设好（默认 npmmirror），日志里能看到实际生效的地址：

```
       Electron binary mirror: https://npmmirror.com/mirrors/electron/
       NSIS binaries mirror: https://npmmirror.com/mirrors/electron-builder-binaries/
```

这两个变量是给 **app-builder.exe**（Go 写的）看的，不是 npm 的配置，所以只设 `npm config` 对打包无效。

| 想做的事 | 怎么做 |
|---|---|
| 换一个 Electron 镜像 | 调用脚本前 `set "ELECTRON_MIRROR=https://mirrors.huaweicloud.com/electron/"`（华为云，已验证可用） |
| 换 electron-builder 那两组 | `set "ELECTRON_BUILDER_BINARIES_MIRROR=<镜像根>/"` |
| 用回 GitHub 官方源 | `set DOWNLOAD_MIRROR=off` |
| 只单独准备 winCodeSign 缓存 | `powershell -NoProfile -ExecutionPolicy Bypass -File scripts\prepare-win-codesign.ps1` |
| 让 `npm install` / `npm ci` 也能下 Electron | 装依赖前 `set ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/`（`@electron/get` 认这个变量） |

下载过的包会留在 `%LOCALAPPDATA%\electron\Cache`（Electron 本体）和 `%LOCALAPPDATA%\electron-builder\Cache`（NSIS / winCodeSign），之后断网也能打包；想强制重下就删掉对应目录。

### 顺带修掉的：非管理员打包报 `Cannot create symbolic link`

`winCodeSign-2.6.0` 里有 `darwin\10.12\lib\libcrypto.dylib`、`libssl.dylib` 两个 macOS 符号链接。7za 解压时要在 Windows 上创建符号链接，**普通权限做不到**：

```
ERROR: Cannot create symbolic link : 客户端没有所需的特权 : ...\Cache\winCodeSign\<随机数>\darwin\10.12\lib\libcrypto.dylib
⨯ cannot execute  cause=exit status 2
  • Above command failed, retrying 3 more times
```

（没开"开发者模式"、又不是管理员时 100% 复现；管理员或开发者模式下不报错。）偏偏写 exe 图标和版本信息用的 `rcedit-x64.exe` 就在这个包里，不解压就出不了安装包。

app-builder 的判断是"缓存目录已经存在就直接用，不再下载也不再解压"，所以脚本第 4 步会先跑 `scripts\prepare-win-codesign.ps1`：从同一个镜像下这个 7z、校验 SHA-512（跟 app-builder 自己校验的值一致）、解压时只跳过那两个 macOS 符号链接（Windows 构建永远用不到），放到 `%LOCALAPPDATA%\electron-builder\Cache\winCodeSign\winCodeSign-2.6.0`。这样**不开管理员权限也能打包**。脚本失败时只打 `[WARN]`，管理员权限下 electron-builder 仍会自己解压，不影响原来的流程。

> 上面"需要管理员权限"那条针对的是 `demo\` 目录的 ACL（写 `demo\logs\` 会 `Access is denied.`），跟这里的符号链接是两件事；ACL 修好之后，普通权限就能完整打包了（本机已实测通过）。

## 改版本号

版本号只有一个入口，别手改单个文件：

```powershell
# 查看当前版本、以及各处版本号是否一致
node scripts\version.mjs

# 改成 0.2.4（加 --write 才真正落盘）
node scripts\version.mjs 0.2.4 --write

# 只校验不改（CI 用）：--check 比对各处是否一致，--check-tag 额外要求 git 里已有该 tag
node scripts\version.mjs --check
node scripts\version.mjs --check-tag v0.2.4

# 版本工具自测（改过 scripts\version.mjs 后跑一次）
node scripts\version.test.mjs
```

一次会改动这四处（外加打印仍需人工更新的地方）：

| 文件 | 字段 | 作用 |
|---|---|---|
| `demo\frontend\electron-react-app\package.json` | `"version"` | 唯一真源。electron-builder 据此决定安装包文件名、`app.getVersion()`、`latest.yml` 自动更新源版本 |
| `demo\pom.xml` | `<project><version>` | 后端 jar 版本，写成 `0.2.4-SNAPSHOT`；jar 名 `demo-0.2.4-SNAPSHOT.jar` 由 `electron.js` 按 `demo-*.jar` 通配匹配、由 `electron-builder.yml` 的 `demo-*-SNAPSHOT.jar` 过滤器拷进安装包 |
| `demo\src\main\resources\application.yml` | `app.version` | 后端启动日志的那行「后端版本: x.y.z」与 `GET /api/health` 的 `version` 字段 |
| `demo\frontend\electron-react-app\package-lock.json` | `"version"`（根 + `packages[""]`） | npm 的镜像字段，跟着一起改，避免 `npm ci` 报不一致 |

改完之后，程序里能看到版本号的地方会一起变（都从上面四处推导，没有任何硬编码）：

| 位置 | 取值来源 |
|---|---|
| 设置页 → 关于 → 「版本 x.y.z」 | 渲染进程经 IPC 调 `app.getVersion()`（即 `package.json` 的 `version`），见 `Settings\sections\VersionInfo.tsx` |
| 菜单栏「关于」弹窗 | 同一个 IPC（`App_electron.tsx` 的 `handleAbout`） |
| 前端日志（`logs\log-*.log`） | 主进程启动时打印 `应用版本: x.y.z \| 运行模式: 安装版/开发`，见 `public\electron.js` 的 `initLogFile()` |
| 后端日志（`logs\log-*.log`） | 启动完成时打印 `LimbusCompany Plot Video Generator 后端版本: x.y.z`（读 `application.yml` 的 `app.version`） |
| `GET /api/health` | 返回 `"version": "x.y.z"`，可用来核对前后端是否同一版本 |
| 安装包文件名 / 自动更新源 | electron-builder 读 `package.json` 的 `version` |

`application.yml` 里的 `app.version` 刻意**不用 Maven 资源过滤**（`@project.version@`）：那样只有经过 Maven 构建才会被替换，直接跑源码或用旧 `target\classes` 时会看到过期值；现在的写法保证"源码里写的是什么版本，跑起来就报什么版本"。

改完还要手工做两件事：

1. 在 `docs\版本更新笔记.md` 顶部加一节 `## 0.2.4` 写更新内容（这个文件是发版说明的来源）
2. 提交后打 tag：`git tag v0.2.4`，再 `git push --tags`；`.github\workflows\release.yml` 由 `v*.*.*` 标签触发，并且会在构建前校验 **tag 版本 == package.json 版本**，不一致直接失败

不需要改的地方（都是运行时推导，别写死）：

- `demo\frontend\electron-react-app\public\electron.js` 用 `app.getVersion()` 取版本，不写版本号
- `demo\frontend\electron-react-app\src\...\Settings\sections\VersionInfo.tsx`（设置页版本显示）同样走 IPC，不含版本字面量
- 后端 `MainApplication` / `HealthController` 读的是配置项 `app.version`，不含版本字面量
- `demo\frontend\electron-react-app\electron-builder.yml` 没有 `extraMetadata`、也没有写死版本（只有 `extraResources` 里用 `demo-*-SNAPSHOT.jar` 这种通配过滤器）
- `demo\build-package.bat` / `start_all.bat` 不引用版本号

> 历史坑：v0.1.0 ~ v0.2.2 期间只改了 `版本更新笔记.md` 和 tag，`package.json` 一直停在 `0.1.0`，所以安装包文件名和程序内显示的版本都比实际发版落后。现在 `node scripts\version.mjs --check` 能直接把这种不一致报出来。

## 自动更新（打包时必须一起看）

更新链路：应用 → `public/update-service.js` → electron-updater → `latest.yml` → 安装包。
更新源是 **GitHub 原地址 + 加速前缀**，全部走 `generic` provider（只读
`<源>/latest.yml`），不用 GitHub API；`latest.yml` 里每个文件都带 `sha512`，下载完会校验。

> **每次发版有两个安装包，`latest.yml` 指向的是精简版**（`LCP<版本号>-lite.exe`，约 264 MB）。
> 两个包都会跑到 `--publish always`，但精简版后打、后写 `latest.yml`，所以自动更新拿到的是它。
> 这是有意的：更新只是换程序，用户的素材在自己的数据目录里，覆盖安装不会删；装了完整版的用户
> 更新后也仍然有全套素材（`ensureUserDataFiles` 只在目标不存在时复制，`BundledAssetSync` 只补缺失文件）。
> 顺序别调反 —— 调反了每次自动更新就会去下 800 MB 的完整版。

```
https://github.com/qbbb718/LimbusCompanyPlotVideoGenerator/releases/latest/download/
https://gh-proxy.com/https://github.com/.../releases/latest/download/
https://ghfast.top/https://github.com/.../releases/latest/download/
```

### 三条"缺了就会静默失效"的打包要求

1. **`electron-updater` 必须留在 `dependencies`**（`package.json`）。
   放在 `devDependencies` 时 electron-builder 不会把它打进 asar，安装版里
   `require("electron-updater")` 抛异常、被 `try/catch` 吞掉 → 更新功能整个消失，
   界面上什么都看不出来，日志里只有一行 `electron-updater 不可用`。
   排查方式：

   ```powershell
   npx asar list release\win-unpacked\resources\app.asar | Select-String 'electron-updater'
   ```

   看不到 `\node_modules\electron-updater\...` 就是没打进去。

2. **`electron-builder.yml` 的 `files` 要包含主进程用到的文件**：
   `public/*.js`（`electron.js`、`preload.js`、`update-service.js`、`update-manifest.js`…）
   与 `public/log-export/**/*`（导出日志的 zip 写入器）。用通配而不是逐个列，
   是因为漏一个的后果太难发现：前者会让更新功能静默消失，后者是历史遗漏——
   `electron.js` 里 `require("./log-export/zip-writer")` 但 `files` 里没有那个目录，
   打包出来的安装版会在启动时 `MODULE_NOT_FOUND`（开发模式直接读源码，永远复现不了）。
   `build-package.bat` 打完包会自检这一项，缺了直接 fail。

3. **`app.setAppUserModelId` 要等于 `electron-builder.yml` 的 `appId`**
   （现在是 `com.lbc-plot.video-generator`）。Windows 的 Toast 通知依赖它，
   少了它就"下载完成"的通知不弹。

### 怎么验更新功能（不用每次都打 800MB 的完整包）

electron-updater 支持开发模式读 `dev-app-update.yml`，可以在 `npm run electron` 里把
"发现新版本 → 下载进度 → 重启安装"这套界面走通：

```powershell
# 1) 前端目录下放一个 dev-app-update.yml（不提交也行，仅本地测试用）
#    provider: generic
#    url: http://127.0.0.1:9000
# 2) 起一个静态服务器，指向打包产物目录（里面有 latest.yml 与 LCP*.exe；latest.yml 指向精简版）
npx http-server release -p 9000
# 3) 让 dev 模式也走更新流程（否则 app.isPackaged=false 会直接跳过）
$env:LBC_UPDATE_DEV='1'; npm run electron
```

界面路径：设置 → 软件更新。想造"有新版本"，把静态目录里 `latest.yml` 的 `version` 改大即可
（`sha512`/`size` 必须和同目录下的 exe 对得上，否则下载校验会失败——这正好用来验校验逻辑）。
`quitAndInstall` 在 dev 模式下不会真的覆盖安装，**静默安装只能打真包验证**。

### 发版时的更新说明

`docs/版本更新笔记.md` 是该版本说明的唯一来源，CI 会：

```powershell
node scripts/changelog.mjs --version v0.6.0 --out release-notes.md          # → Release 正文
node scripts/changelog.mjs --json demo\frontend\electron-react-app\release\changelog.json  # → release 资产
```

- Release 正文会被 electron-updater 当作 `releaseNotes` 带进应用（更新源走 GitHub 时）
- 走加速通道时应用读 `changelog.json`（就在 `latest.yml` 旁边），所以两样都要上传
- 该版本在更新笔记里没有 `## x.y.z` 一节时 CI **直接失败**，不会打出"更新内容空白"的安装包

### 需要真机确认的一次性验证

自动更新在 assisted 安装器（`oneClick: false`）下靠注册表里的 `InstallLocation` 决定装回哪里。
本地装到非默认目录（例如 `D:\LBC`）后，走一次真实的自动更新，确认新版仍然落在 `D:\LBC`。
（`/D=` 只在"路径没有空格"时才由应用自己传：NSIS 要求 `/D=` 是最后一个参数且不能加引号，
路径里有空格或运行在 `win-unpacked` 里时，应用会退回带界面的安装向导。）

### 先跑一次后端自检（强烈建议）

打包脚本第 2 步产出的 jar 可以直接自检，不用启动界面：

```powershell
java -jar demo\target\demo-0.2.3-SNAPSHOT.jar --self-check=webp
```

它不启动 Spring、不连数据库、不碰用户数据目录，只做三件事：预热 FFmpeg 原生库、
现场解码一张内联的最小 WebP（校验 alpha 与通道顺序）、打印 ffmpeg/ffprobe 的实际路径。
通过时打印 `[SELF-CHECK] PASS webp 8x4 cacheDir=...` 并返回 0，失败返回 1 并把完整异常链写进日志。

**为什么必须用 `java -jar` 跑**：WebP 立绘靠 JavaCV/FFmpeg 的原生库解码，而
`mvn spring-boot:run` / IDE / `mvn test` 用的是扁平 classpath，原生 jar 是磁盘上的真实文件，
JavaCPP 直接就能加载 —— 本地永远看不出问题。只有 `java -jar`（Spring Boot 可执行 jar，
原生 jar 嵌在 `BOOT-INF/lib/` 里）才会暴露"原生库没能释放出来"的故障。

日志里这几行是排查"立绘显示成红色『加载失败』方块"的关键：

| 日志 | 含义 |
|---|---|
| `JavaCV 原生库来路: jar:nested:...!/BOOT-INF/lib/javacpp-...jar!/（Spring Boot 嵌套 jar：需要 JavaCPP 释放到缓存目录）` | 安装版的真实形态；对照本地开发会是"扁平 classpath：磁盘真实文件" |
| `JavaCPP 缓存目录: %LOCALAPPDATA%\limbus-plot-video-generator-javacpp` | DLL 会被释放到这里（固定目录，不是临时目录，不会被清理策略波及） |
| `FFmpeg 原生库预热完成（JavaCV 可用）` | 正常 |
| `FFmpeg 原生库不可用，WebP 立绘将无法解码（会显示为红色"加载失败"占位图）。原因: ...` | 出问题了，后面几行 `caused by:` 才是真根因（例如 `UnsatisfiedLinkError: no jniavutil in java.library.path`） |
| `已用 FFmpeg 解码 WebP: ... => 宽x高` | 实际解码成功的证据 |

> 排查提示：如果是最坏情况（原生库真的起不来），可以先把
> `%LOCALAPPDATA%\limbus-plot-video-generator-javacpp` 整个删掉再启动一次 ——
> 它只是可再生成的缓存，删掉会强制从安装包里的原生 jar 重新释放一遍，
> 能顺带排除"被杀软隔离/清理工具删掉一半 DLL"这种情况。

### 立绘的 WebP → PNG 入库转换

上传立绘时如果文件是 WebP，后端会**当场用 FFmpeg 解一次并转成 PNG 存盘**，原图备份到角色目录下的
`originals/`。这样渲染路径读到的永远是 PNG（JDK 自带解码器），不需要 FFmpeg 去解图片。

| 现象 | 说明 |
|---|---|
| 上传 WebP 报"这张 WebP 立绘无法解码，已取消上传" | 原生库或文件本身有问题；**不会**留下半成品文件，用户重试或换文件即可 |
| 立绘目录下同时有 `{portraitId}.png` 和 `originals/{portraitId}.webp` | 正常：PNG 是渲染用的副本，原图是转换可回退的备份（删除立绘时一并清理） |
| PNG 比原 WebP 大约 11 倍 | 预期行为（实测 116KB → 1.3MB）。导入只发生一次，不影响渲染性能 |
| 老素材里还有 `.webp` | 也正常：那批没经过转换，读取时仍由 FFmpeg 兜底，能正常显示 |

> 只想验证"打包后的 jar 能不能解 WebP"时用上面的 `--self-check=webp` 就够了，
> 不需要真的启动界面并上传文件。
