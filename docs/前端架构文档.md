# 前端架构文档

本文档描述前端应用（`demo/frontend/electron-react-app`）的架构设计、组件组织、状态流转与主进程协作方式。

- 后端渲染管线与业务逻辑 → `项目文档.md`
- REST 接口细节 → `API文档.md`
- 模型字段（Java 侧） → `前端模型.md`

## 技术栈

| 方面 | 选型 | 说明 |
| --- | --- | --- |
| UI | React 19 + TypeScript 4.9.5 | 不使用组件库，全部手写组件 + CSS |
| 构建 | Create React App 5（`react-scripts`）+ `@craco/craco` 7 | craco 只用于路径别名与 Jest 映射，见 `craco.config.js` |
| 桌面外壳 | Electron 39 | 主进程 `public/electron.js`，预加载 `public/preload.js` |
| HTTP | Axios 1.x | 统一封装在 `features/common/ApiService.ts` |
| 日志 | electron-log 5 | 渲染进程 console 经 IPC 落到主进程日志文件 |
| 图像 | react-advanced-cropper（裁剪）/ react-colorful（色板）/ react-easy-crop（只用到它的 `Area` 类型） | 立绘裁剪、名片与自由文本的颜色面板 |
| 屏幕取色 | Electron `desktopCapturer` + 全屏遮罩窗口（`public/color-picker.js`） | 颜色面板的吸管：可吸软件窗口以外的颜色 |
| 打包 | electron-builder 25 + electron-updater 6 | 出 NSIS 安装包、检查自动更新 |
| 测试 | Jest + Testing Library（CRA 自带） | `npm test` |

路径别名（`tsconfig.json` 的 `paths` 与 `craco.config.js` 的 `alias` / Jest `moduleNameMapper` 各配一份，缺一处编译或单测就会失败）：

| 别名 | 指向 | 备注 |
| --- | --- | --- |
| `@features/*` | `src/features/*` | 业务代码主体 |
| `@services/*` | `src/services/*` | 垫片，转出 `features/common/ApiService` |
| `@types/*` | `src/types/*` | 垫片，转出 `features/common/types` |
| `@root/*` | `src/*` | 垫片目录与 `appConfig` 用得多 |

## 应用入口与页面框架

`src/index.tsx`：

1. `React.StrictMode` 挂载到 `#root`
2. 用 `navigator.userAgent` 是否含 `electron` 判断运行环境
3. Electron 窗口 → `AppElectron`；浏览器（`npm start` 直接打开）→ `App`
4. 注意 `@features/app` 的默认导出**就是** `AppElectron`

`features/app/App_electron.tsx` 是整个界面的宿主，负责：

1. **持有设置**：`projectSettings`（初值 `loadSettings()` 读 localStorage）与 `activeTab`
2. **持有工程**：`const workspace = useProjectWorkspace(projectSettings.name)`（见状态管理）
3. **启动初始化**：`ApiService.healthCheck()` → `getSettings()` 与本地设置对齐 → `initAudio()`；任一步失败只打 `warn`，不阻塞界面
4. **设置持久化**：`projectSettings` 每次变化即写 localStorage；`outputPath` 变化后防抖 800ms 再 `PUT /api/settings` 同步到后端
5. **订阅菜单事件**：新建 / 打开 / 保存 / 导出 / 关于（见「菜单与快捷键」）
6. **渲染页签**：剧情编辑 / 资源管理 / 文本转记录 / 设置 + 全局 `ProjectToast`

页签与组件的对应关系：

| 页签 | 组件 | 入口 |
| --- | --- | --- |
| 🎬 剧情编辑 | `RecordEditor` | `@features/record`（默认导出） |
| 📦 资源管理 | `ResourceManager` | `@features/resource` |
| 📝 文本转记录 | `TextToRecords` | `@features/text-to-records` |
| ⚙️ 设置 | `Settings` | `@features/settings` |

**页签切换会卸载当前页面组件**（`renderActiveTab()` 每次返回新的元素）。所以"当前工程"（记录、分组、选中位置、当前属性页签）必须放在 App 层的 `useProjectWorkspace` 里；如果放回编辑器内部 state，切到资源管理再回来，编辑内容就会被后端数据覆盖。

`features/app/App.tsx` 是浏览器调试版：布局相同，但不做后端初始化、不订阅菜单、初始页签是"文本转记录"，设置类型用 `features/app/types.ts` 的精简版。

## 组件架构

### 1. 剧情编辑器 (RecordEditor)

**路径**: `features/record/`

**职责**: 左上是单条记录的预览图与时间轴，右上是该记录的属性面板，下方是整部剧情的列表（分组、拖拽排序、工程读写、分层导出视频）。

**组件层级**:

```
RecordEditor (RecordEditor.tsx)              # 持有一份 cameraEditor（摄像机页签 ⬌ 世界视图共用）
└── DockLayout (dock/DockLayout.tsx)         # 三块区域 = 可拖动、可拼合、可拖出的面板
    ├── DockToolbar                          # 面板菜单（查看/恢复隐藏面板）/ 重置布局 / 操作提示
    ├── DockGroupChrome × N                  # 主区域页签组：页签（拖拽手柄 ⠿）+ 最大化 / 浮动 / 隐藏
    │   └── DockTabs                         # 每个面板一个页签，点 = 切换，拖 = 停靠/拖出
    ├── 分割线（可拖动；键盘 ← → ↑ ↓ 微调）

    │   ├── PropertyTabs + 当前页签内容       # 属性
    │   └── RecordList                       # 剧情记录
    └── 拖拽层：ghost + 停靠指示器 + 「松开 → 独立窗口」提示
```

**属性面板内容**:

| 页签 | 主要内容 |
| --- | --- |
| 文本 | 说话人下拉（旁白 / 自由文本 / 角色，角色项带默认立绘小头像）、手动说话人名称、阵营、自由文本样式（加粗 / 斜体 / 隐藏UI / 文字颜色 / 文字位置 X、Y 及滑块与归零）、对话内容（textarea，**支持换行**：Enter 换行，预览与成片按换行分段；下方提示显示行数 / 字数）、场景（`location`）、显示速度 1–6，以及"⚙️ 全局显示速度设置"（跳到全局页签并高亮滑块） |
| 立绘 | 每个角色视觉元素：角色下拉、立绘缩略图（点击更换）、立绘压暗、缩放（数值框 + 滑块 + 复原，以脸部裁剪框中心为基准）、X 坐标（数值 + 滑块 + 7 个快速定位点）、Y 坐标、上移 / 下移 / 删除；"添加新立绘"（临时图片已拆走，见下一行） |
| 临时图片 | 与「立绘」同级的独立页签（原先挂在立绘页签底部）：路人 / 道具列表 — 标题行缩略图（48×48，失败露出 "?" 占位）、缩放、是否压暗、X / Y 坐标、删除；"添加临时图片" |
| 背景 | 当前记录的背景列表（每项带 16:9 缩略图，失败回退原图）：缩放、X / Y 坐标偏移（0 = 居中，数值不设上下限，滑块范围随缩放扩大）、三行各自的 ↺ 图标复原按钮（只复位本行）、**压暗开关**（每条背景独立，压暗一半，只压这一层，预览与成片同时生效）、删除；选择器（搜索、双击缩略图直接添加、缩略图失败回退原图） |
| 摄像机 | 与「立绘」「背景」同级的独立页签（原先浮在预览画面上的工具条）：状态摘要（静止 / 运镜 N 帧 + 取景框读数）、编辑起点 / 终点、中心读数、缩放（± 按钮 + 滑杆）、缓动、运镜时长、▶ 播放 / 复位镜头 / 适配视图 / 铺满背景、**预设**（镜头摇动等镜头层效果，注册表驱动，见「摄像机预设（C3）」）、拖动工具（移镜 / 移元素）。**进这个页签时预览切到世界视图**（`CameraModeView`），离开即回到成片 |
| 音效 | 当前记录的音频指令列表 + 选择器（搜索、双击直接添加、类型 BGM / 语音 / 音效） |
| 特效 | 记录级**起始转场**（三种互斥，勾一种会取消其它两种）：交叉溶解（叠前一条记录的最后一帧）、黑屏转场（整屏叠纯黑）、白屏转场（整屏叠纯白）。勾选后导出视频时，该条记录开头 20 帧在上方叠加对应图像，不透明度从 100% 线性降到 0%；只影响视频（预览图与记录时长不变），第一条记录勾交叉溶解时会提示没有上一条可叠。**镜头摇动不在这里**（已迁到「摄像机 → 预设」），页签底部留一句指路说明 |
| 全局设置 | 项目名称、剧情类型、视频尺寸、文字显示速度（全局）、BGM / 语音 / 音效音量、输出路径（浏览） |

**数据流**:

1. 记录不放在组件 state，来自 `props.workspace`（`useProjectWorkspace`，见状态管理）
2. 选中项只记下标 `selectedRecordIndex`；拖动 / 分组重排后统一走 `applyRecords()` —— 按 **uuid** 找回选中项的新下标，并用 `syncGroupAnchors()` 同步空分组位置，所以预览和属性面板不会跳到别的记录
3. 属性编辑 → `updateRecord(index, record)` → 新数组写回 workspace，并把 `isDirty` 置 `true`
4. `RecordPreview` 用"视觉摘要"（chars / bg / tempImages / audioCommands / dialogue 中的视觉字段）判断是否 `forceRefresh`：摘要变了才强制后端重渲染，否则复用后端缓存；`plot`（剧情类型）变化也会重新取图
5. 新建记录会继承当前记录的立绘、背景、临时图片、说话人与音频指令；文字样式（自由文本 / 加粗 / 斜体 / 隐藏UI / 颜色 / 位置）沿用上一条；`dialogue.speed` 取全局 `textSpeed`。在分组内点 `+` 会插到该组末尾并自动展开分组；工程为空时自动补一条空记录（`autoCreatedRef` 防止 StrictMode 下 effect 重跑出两条）
6. 分组内新增、上移下移、拖拽、复制、删除都调用 `recordGroups.ts` 的纯函数（`newRecordInsertIndex`、`neighborMoveTarget`、`moveRecords`、`moveGroup`、`syncGroupAnchors`），保证"同一分组的记录在数组里始终连续"——播放顺序与列表顺序一致
7. 导出视频：`RecordList` 弹分层选择 → `generateVideo(layerTypes, keepTempFiles)` → `ApiService.generateVideo()` 拿到 `taskId` → 每秒 `getVideoProgress()` 轮询 → 完成弹 `ExportSuccessDialog`，失败 `alert`；另设 30 分钟兜底定时器避免轮询永远不停
8. 全局文字速度不只是写设置：`GlobalProperties` 改动后还会用 `withGlobalTextSpeed()` 把新档位覆盖到所有已有记录

**剧情列表的交互约定**（`RecordList.tsx` + `recordGroups.ts`）:

- 单击选中；`Ctrl` 追加、`Shift` 连选；多选后可一起拖
- 拖动左侧 ⠿ 手柄：可放到某条记录前 / 后（会加入该记录所在分组，目标未分组则一起变为未分组）、放进某个分组、放到列表最前 / 最后（同时移出分组）
- 拖动时列表上下边缘出现两行放置区（"放到列表最前面 / 最后面"）。这两个放置区必须**延后一轮渲染**才出现：拖动源上方在 `dragstart` 当轮突然多出节点时，Chromium 会直接取消整个拖拽
- 分组表头：`▾/▸` 折叠、双击名称或 ✎ 重命名、🗑 解散（组内记录保留为未分组，需确认）、拖表头调整分组顺序；空分组用 `anchorUuid` 记住显示位置
- 折叠的分组只隐藏记录行，记录仍在 `records` 数组里，播放顺序不变

**可停靠面板系统**（`features/record/dock/`，主组件 `DockLayout`）：

- **布局树**：两种节点 —— `split`（`orientation: row | column`，子节点 `size` 比例）与
  `tabs`（`panels[]` + `activePanel`），可任意嵌套。操作全是纯函数：
  - `insertPanelIntoTab` / `splitTabWithPanel` / `removePanelFromTree`：空页签组消失、
    只剩一个子节点的分栏会被提升（不留单叉分栏）；
  - `dockPanelInState`（先移除再插入，支持主区域 ⇄ 独立窗口）、`detachPanelInState`、
    `dockWindowInState`、`closeWindowInState`、`showPanelInState`、`toggleMaximizeInState` 等
    操作整份 `DockState`；
  - 每个面板在整份状态里**最多出现一次**；不在任何树里的面板 = 隐藏
    （内容不销毁，可从「面板」菜单或空状态恢复）。
- **拖拽**（`usePanelDrag`，pointer 事件，不用 HTML5 拖放）：
  - 按下页签后**超过 4px** 才进入拖拽，否则按点击切页签；拖拽中给 `<body>` 加
    `.dock-panel-dragging`；
  - 落点判定 `resolveDropTarget`：最上层独立窗口 > 主区域；指针在停靠区外 = 松手变独立窗口；
  - 目标面板四边热区约 64px（按宽高夹在 12%–35%）→ 上/下/左/右分割；中部 → 合并成页签；
  - 停靠指示器**延迟 90ms** 出现（`DOCK_HOVER_DELAY_MS`），快速划过多个面板不会一路闪；
    ghost 始终跟随指针，在区外时显示「松开 → 独立窗口」；
  - `Esc` / `pointercancel` / 窗口失焦取消拖拽。布局只在松手时修改，所以取消不需要回滚。
- **独立窗口**：`x / y / width / height / z` 存停靠表面坐标，渲染时 `clampWindowRect`
  夹回可视区；标题栏拖动、8 向缩放（最小 320×220）；「停靠回主区域」把窗口里的页签并回主区域，
  「关闭」= 面板收进「面板」菜单。点击/拖动窗口会置顶。
- **最大化**：`state.maximized` 记一个主区域面板，`computeLayout` 只返回该组并铺满；
  同组切页签时最大化目标跟随，隐藏/拖出时清除。
- **状态保留**：三块内容渲染在固定顺序的 `.dock-panel-host` 里（key = 面板 id），
  停靠/合并只改 host 的 `left / top / width / height / visibility`，**React 父节点不变**，
  所以面板内部滚动位置、输入内容、选中项不会因停靠而重置；非当前页签 / 隐藏面板用
  `visibility: hidden`（按最后一次的矩形继续排版，不用 `display: none`，浏览器不会清掉滚动位置）
  隐藏但仍挂载。
- **持久化**：`localStorage["lcpgv_record_dock_layout"]`（`DOCK_LAYOUT_STORAGE_KEY`），
  状态变化后防抖 150ms 落盘、卸载前补存；读取时逐字段校验（未知/重复面板、空组、单叉分栏、
  窗口 z 重排、失效的最大化），版本不符或坏 JSON 回落默认布局。隐藏面板不单独存
  （不在任何树里即隐藏），所以将来新增面板也不会"永远找不回来"。
- **空状态**：`dockRoot === null` 时显示恢复入口（恢复隐藏面板 / 停靠全部窗口 / 重置布局），
  独立窗口与菜单仍然可用，不影响页面其它功能。
- **自适应**：各面板内容仍是原来的响应式组件（预览按容器实测等比缩放、属性页签用容器查询换行、
  列表横向滚动）；停靠组标题栏固定 30px，内容区 `min-height: 0` + 自身滚动；
  窄窗口时工具条的标题/提示按容器查询隐藏。
- **测试**：`dockTree.test.ts`（树操作 + 整份状态）、`dockGeometry.test.ts`（矩形摊平 /
  四边中心判定 / 窗口夹紧与缩放）、`dockPersistence.test.ts`（往返 + 坏数据清理）、
  `DockLayout.test.tsx`（页签切换、拖出/停靠/关闭、菜单/空状态/重置、Esc、持久化、
  拖拽合并）；`RecordEditor.test.tsx` 继续覆盖属性页签 ⇄ 预览世界视图的联动。

**资源包导入导出（角色 / 背景 / 音频通用）**:

- 三类资源的交互完全一致：`📤 选择导出` 进入多选模式（卡片/条目出现勾选框 + 工具条出现 `全选`），`✅ 确认导出` 把勾选项（**没勾选时导出当前可见全部**）发给后端打包下载；`📥 导入` 选 ZIP 上传后重新拉列表
- 页面顶部另有 `📦 导出全部资源` / `📥 导入全部资源`：后端把角色、背景、音频、序列帧动画分别放进 `characters/`、`backgrounds/`、`audios/`、`animation-clips/` 四个目录，加一个 `manifest.json`，一次完成整库迁移
  - 动画在包里是"每套一个 `.lcaf`"（没有数据库，素材目录本身就是交换格式）；导入后前端会
    `refreshAnimationClips()` 让模块级素材缓存失效并重拉，否则子页面看到的还是导入前那份列表
- 下载/上传的公共逻辑在 `features/common/utils/resourceTransfer.ts`：`downloadBlob`（Blob → 本地文件）、`zipFileName`（`类型_日期.zip`）、`describeTransferError`（优先显示后端 `message`）
- 后端接口：`POST /api/characters|backgrounds|audios/export|import` 与 `POST /api/resources/export|import`；
  导入一律按"新增"处理（ID 冲突时后端分配新 ID），不会覆盖本机已有资源

**数据流**:

1. `ResourceManager` 挂载时 `Promise.all([getCharacters, getBackgrounds, getAudios])`，并把背景的 `path` / `thumbnailPath` 规整成可直接给 `<img>` 的绝对 URL
2. 搜索：`ResourceManager` 用 `searchTerm` 过滤后把结果作为 props 往下传（背景 / 音频 Tab 内部还会再按同一关键字过滤一次，结果一致、无副作用）
3. 上传：原图走 `multipart/form-data`（`uploadPortraitFile` / `uploadBackgroundFile` / `uploadAudioFile`），缩略图单独上传（`uploadPortraitThumbnail` / `uploadBackgroundThumbnail`）；背景缩略图在客户端用 canvas 生成
4. 删除：卡片或条目上的悬浮按钮 → **只弹一次**确认 → 带 `deleteFiles` 调后端（角色会连同立绘原图与缩略图一起删）
5. 新角色在"添加立绘"前会先静默保存一次（否则后端找不到角色），成功后 `characterPersisted` 置真

**默认立绘**: 唯一真源是后端返回的 `Portrait.defaultPortrait`（数据库 `character_portraits.is_default`）。`utils/portraitUtils.ts` 提供 `getDefaultPortrait` / `isDefaultPortraitId` / `markDefaultPortrait`，取不到标记时才回退到 `portraits[0]` 兼容旧数据。不要再按"列表第一项"判断默认立绘——按 `port_name` 排序或改名都会让它漂移。

**立绘列表顺序**: 默认立绘**永远排在立绘列表第一张**（资源管理 → 角色 → 立绘）。后端 `GET /api/characters` 返回的顺序已经是"默认立绘在前、其余按名称"（`PortraitDAO.findByCharacterId` 的 `ORDER BY COALESCE(cp.is_default, 0) DESC, p.port_name`），但本地改动会打破它，所以：

- `orderPortraitsDefaultFirst()`（`utils/portraitUtils.ts`）是**唯一的排序入口**：默认立绘挪到首位，其余保持原相对顺序；已经排好的列表原样返回同一引用。`PortraitsSection` 渲染前过一遍，`CharacterDetailModal` 在初始状态 / 同步父组件数据 / 新增 / 批量导入 / 删除后也过一遍 —— 数据从哪条路径来都不会出现"默认立绘排在中间"
- `markDefaultPortrait()` 取消旧标记后会顺手把新的默认立绘置顶（点「设为默认」当场换到第一张），不再只改角标
- 删掉默认立绘时，`CharacterDetailModal` 与 `DELETE /api/characters/{cid}/portraits/{pid}` 都会把剩下的第一张提为默认（后端只删这一条关联，不再误删该角色全部关联记录）
- `PUT /api/characters/{id}` 的响应里，立绘顺序与 `defaultPortrait` 标记按库里的结果回填（`CharacterController.orderPortraitsDefaultFirst`），所以"保存 → 重新打开"不会因为入参顺序不同而挑错默认立绘

**缩略图缓存（同名覆盖 → 只能靠版本号换地址）**:

立绘缩略图的服务端文件名是**固定的** `thumbnail_{portraitId}.png`：裁剪改完、甚至换一张原图，后端都是**覆盖**同名文件，`Portrait.thumbnailPath` 一个字都不变。而浏览器缓存按 URL 认图，所以"改完裁剪、回到列表看到的还是旧头部的图，要关掉角色弹窗重新打开才变"（重新挂载才会重新拼一次带时间戳的地址）。

- 立绘列表：`CharacterDetailModal` 维护 `thumbnailVersions`（立绘ID → 代次），`PortraitCard` 把它当 `cacheBust` 传给 `PortraitThumbnail`，后者据此拼一个新的 `?t=` 时间戳。立绘编辑器保存（`handlePortraitSaved`）只给**这一张** +1；「与默认立绘裁剪一致」按 `updatedPortraits` 的 ID、「批量导入立绘」按新导入的 ID 分别 +1 —— 不用一个全局版本号，否则批量导入 40 多张会让整个列表的缩略图全部重新下载一遍
- `PortraitThumbnail` 只在 `(characterId, portraitID, thumbnailPath, 代次)` 真的变了才重算 URL；`data:` / `blob:` 地址不加时间戳（加了反而打不开），老数据只存文件名时按角色素材根目录兜底（`buildPortraitThumbnailUrl`）
- 角色卡片头像 `CharacterAvatar` 的 key 是 `(characterId, thumbnailPath, 裁剪框)`：裁剪改了 key 就变，头像跟着换图；key 不变时地址不变。原来的实现是渲染里现算 `?t=${Date.now()}`，搜索框每敲一个字都会把几十张头像重新解码，主线程被占满后输入框会"打不了字、丢焦点"（见 `CharacterAvatar.test.tsx` 的回归测试），加裁剪框只是把这个 key 补全，不能退回渲染里现算
- 背景缩略图不需要这套：文件名里带时间戳（`thumb_{bgId}_{ts}.jpg`），换了就是新地址

**情绪与立绘**:

- 情绪下拉框只显示中文关键词（正常 / 开心 / 悲伤 / 生气 / 惊讶 / 困惑 / 害羞 / 受伤），选项 `value` 仍是后端认识的小写 code；旧数据里的大写枚举名（`HAPPY`）由 `mapEmotion()` 归一化
- 选择立绘文件时，`detectEmotionFromFileName()` 会按文件名自动识别情绪（中英文关键词都支持：`罗佳-face_happy_L.png` → 开心、`罗佳-悲伤.png` → 悲伤）；识别不到时**保留用户当前选择**，不会退回"正常"
- 裁剪框语义：从下巴框到头顶（不含头发厚度），`length` 参与画面里的缩放计算
- **保存 / 取消在标题栏**：和「角色编辑」弹窗一致放在 `.modal-header` 的 `.header-actions` 里（`.btn-primary` / `.btn-secondary` + 关闭 `×`），底部 `.modal-footer` 已经删掉。`.portrait-modal` 把标题栏钉成固定 64px、裁剪画布与设置面板放进 `.modal-body` 自己滚 —— 窗口只有 700px 高时也先看得见保存按钮，不用把弹窗滚到底；「添加新立绘」还没选文件时（`editingPortrait` 仍是 null）保存置灰并提示「请先选择立绘文件」
- **头部裁剪示例图随前端打包**：`PortraitSettings` 直接 `import` `PortraitModal/assets/head-crop-guideline.png`。以前拼的是 `${BASE_URL}/assets/guides/head-crop-guideline.png`，可这个文件从未进过数据目录 / 安装包，界面上一直是裂图 —— 它是界面说明图，不是用户素材，不该走素材目录（打包后落到 `build/static/media/`，`homepage: "./"` 下用相对地址，`file://` 与 dev server 都能加载）

**立绘场景预览**: `PortraitModal` 裁剪区下方右侧的「预览」按钮会打开 `PortraitScenePreview`，把当前裁剪框、角色身高与所选背景提交给 `POST /api/portraits/preview`，后端复用视频静态帧渲染器返回一张「背景 + 立绘 + 边框 + 界面 UI」的 PNG（不包含台词与角色名片）；弹窗底部可切换背景，切换即重新请求。新立绘还没上传时直接以 multipart 传文件，因此预览不会提前把文件写进角色素材目录。

**预览里的对比角色**: 底部「＋ 添加对比角色」展开 `PortraitComparePicker`（预览弹窗内部的绝对定位浮层，不走 ModalPortal）：第一次展开才 `getCharacters()` 拉素材库（不给预览本身增加一次请求），先选角色再点立绘，可加 1~2 个；当前正在编辑的那张会从列表里隐藏。请求时每个对比角色追加一个重复的 `compare` 字段（`立绘ID:水平偏移`，偏移 = 间距百分比 × 1920），后端按 ID 读出它们的裁剪参数，走同一套身高 + 裁剪规则一左一右画在当前立绘**下层**；因此头框（恒为 183 设计像素）在画面里直接可比。间距滑杆只在 `pointerup` / `keyup` / `blur` 时提交，拖动过程不发请求；`Esc` 先收起选择器，再按一次才关预览。

**角色名片刷新**: `NamePreview` 默认显示后端已保存的 `characterCardImagePath`（带 `?v=` 防缓存）；右上角「刷新」把弹窗里**当前参数**（名称 / 阵营 / 颜色 / 身高）发给 `POST /api/character-card/preview` 即时渲染。该接口不读也不写名片缓存，所以改完参数不必先保存就能看到效果；参数一变，之前刷新出来的图立即失效，回退显示已保存名片。

### 3. 文本转记录 (TextToRecords)

**路径**: `features/common/components/TextToRecords/`

**职责**: 把剧本纯文本解析成记录数组并交给编辑器。

**组件层级**:

```
TextToRecords
├── TextInputArea       # 文本域 + 拖入 .txt 读取
├── ConvertActions      # 转换 / 清空
├── ResultDisplay       # 状态文字
└── FormatHelp          # 格式说明与示例
```

**文本格式**:

```text
[BGM名称]
{背景图片名称}
说话人: 对话内容(情绪)%位置%
旁白: 对话内容
[-STOP]
```

- 冒号兼容 `:` / `：`，情绪括号兼容 `()` / `（）`，位置百分号兼容 `%` / `％`
- `%位置%`：角色在画面中的横向位置（百分比），`%0%` 最左、`%50%` 画面中间、`%100%` 最右；不写默认居中
- `[BGM名称]`：切换 BGM（按名称或文件名在音频库里找），出现新 BGM 时上一首自动停止；`[-STOP]` 停止当前 BGM
- `{背景图片名称}`：切换背景，按名称或文件名匹配图库
- `旁白`：底部文本框左侧的角色名 UI 不显示

**数据流**:

1. 用户输入或拖入文本 → `handleConvert()`
2. `ApiService.textToRecords(text)` → `POST /api/text-to-records`，后端返回 `Record[]`
3. `onParsedRecords(records)` → `App_electron.handleParsedRecords` → `workspace.adoptParsedRecords(records)`（归一化成前端结构、清空工程文件关联）→ 自动切到"剧情编辑"
4. 这批记录还没关联工程文件：按 `Ctrl+S` 会先弹保存对话框，不会覆盖之前导入的工程

#### 日志导出 (LogExportSection)

用户的日志藏在数据根目录的 `logs/` 下（默认 `%APPDATA%\limbus-company-plot-video-generator\logs`，
用户可以在设置页把数据根目录换到别的盘），让普通用户自己翻不现实。设置页提供「获取日志」按钮，点一下就能拿到可直接发给开发者的压缩包。

**数据流**（全程不经过后端 HTTP）:

1. 渲染进程 `window.electronAPI.exportLogs()`（`public/preload.js`）→ IPC `logs:export`
2. 主进程 `public/electron.js` 的 `logs:export` 处理器：
   - 定位日志目录：就是本次运行在写的那个目录（`getLogDir()` 返回模块级的 `logDir`）：安装版 `{dataRoot}/logs`，开发模式 `demo/logs`
   - `collectLatestFiles(logDir, 10)` 取最新 **10** 个文件（不足 10 个则有多少拿多少，含子目录；用 `lstat` 跳过符号链接）
   - `createZipBuffer()` 在内存里建包（`public/log-export/zip-writer.js`，deflate + CRC-32，包内目录名 `logs-<时间戳>`）
   - 先建包再弹 `dialog.showSaveDialog()`：压缩失败应在弹窗之前就报错，而不是用户选完路径才看到"导出失败"（用户取消 → `{ ok:false, canceled:true }`）
   - 用户手删了 `.zip` 后缀会自动补回
3. 界面显示导出结果（文件数、压缩后体积、保存路径），用户把压缩包发给开发者

**注意**: 打包和写盘都在主进程完成，渲染进程没有文件系统权限，也不该知道日志目录的绝对路径；zip 由 Node 内置 `zlib` 手工组装（`archiver` 之类的三方库只在 devDependencies，安装版的 app.asar 里没有），这样"应用出问题时取日志"不会因为依赖缺失而失效。

### 工程工作区 (useProjectWorkspace)

**路径**: `features/record/useProjectWorkspace.ts`

把"当前正在编辑的工程"提升到 App 层，一次解决四个问题：页签切换不丢内容；`Ctrl+S` 先存后改；按钮与菜单共用同一套保存/导入逻辑；分组也随工程往返。

对外暴露：

| 名称 | 类型 | 说明 |
| --- | --- | --- |
| `records` | `Record[] \| undefined` | `undefined` 表示首次加载中 |
| `groups` | `RecordGroup[]` | 分组名称、折叠状态、空分组锚点 |
| `selectedRecordIndex` | `number` | 当前选中记录下标 |
| `activePropertyTab` | `PropertyTab` | `text` / `characters` / `tempImages` / `background` / `effects` / `audio` / `global` |
| `filePath` / `fileName` | `string \| null` | 已关联的工程文件；`null` 表示还没保存过 |
| `projectGeneration` | `number` | 新建工程的代次（每新建一次 +1）；编辑器据此补空白记录、清撤销栈 |
| `isLoadingProject` | `boolean` | 首次从后端加载工程记录中 |
| `toast` / `showToast` / `dismissToast` | — | 文字提示（成功 3s、说明 3s、失败 5s 后自动消失） |
| `saveProject` | `() => Promise<boolean>` | 已关联文件就地更新，否则弹保存对话框；返回是否真的存下来了 |
| `newProject` | `() => Promise<void>` | 新建工程：先问「保存并新建 / 不保存 / 取消」，再清空剧情列表 |
| `importProject` | `(file?: File) => void` | 传页面文件选择框拿到的 `File` 直接解析；不传则弹 Electron 原生打开对话框 |
| `adoptParsedRecords` | `(records: Record[]) => void` | 接入"文本转记录"的结果 |

实现要点：

- 保存 / 导入回调用 `ref` 镜像最新状态，保持**稳定引用**：`Ctrl+S` 的 keydown 监听只注册一次、菜单事件不会因为编辑内容变化而反复解绑重绑
- 首次加载：`ApiService.getRecords()`（后端 `{dataRoot}/data/records.json`）→ `normalizeRecords()`；**只有在 `records` 仍为 `undefined` 时才写入**，避免把用户在加载期间刚从"文本转记录"或导入得到的记录冲掉
- 导入：本地解析（保证结构与编辑器完全一致）成功后，异步补一次 `ApiService.importRecords()` 同步到后端；失败只打 `warn`，不影响已打开的工程
- `Ctrl+S`：监听 `keydown`，命中 `Ctrl/⌘+S` 时 `preventDefault`（拦掉浏览器"保存网页"）；Electron 菜单的"保存项目"也绑到同一个 `saveProject`（菜单快捷键会先于页面 keydown 生效）
- 浏览器环境 / 主进程还是旧版本（没有 `writeFile`、`saveProjectFile`）时降级为"下载工程文件"，保证不会出现完全存不下来的情况

**新建工程**（`newProject`，工具条最左的「新建工程」按钮与菜单「文件 → 新建项目」Ctrl+N 共用）：

1. 有记录时先弹三选一确认框（`askChoice`）：**保存并新建 / 不保存 / 取消**；空工程直接新建，不打扰用户
2. 「保存并新建」调 `saveProject()`：**返回 false（保存失败、或在系统保存框里取消）就不清空**——破坏性操作宁可失败
3. 清空 `records` / `groups` / 选中位置 / `activePropertyTab`，并把 `filePath` 置 `null`（新工程没有文件名，
   之后的 Ctrl+S 会先让选位置，不会覆盖上一个工程）
4. `projectGeneration + 1`：编辑器（`RecordEditor`）看到代次变化后清空撤销栈、清掉预览选中态；
   同时那条"空工程自动补一条空白记录"的 effect 会把空白记录补回来（与首次启动的空工程一致）
5. 异步把空工程同步到后端 `data/records.json`（它只是启动初始数据，不一起清掉的话重启后旧记录会"复活"）

### 工程文件与分组

**工程文件格式**: 顶层就是一个记录数组（与后端 `RecordsIO` 导出一致），`JSON.stringify(..., null, 2)` 缩进。分组信息作为 `group: { id, name, collapsed }` 快照附在**每条带分组的记录**上（`recordGroups.stampGroups`），所以文件仍是后端认识的纯记录数组，老版本也能打开。

**分组的数据模型**（`recordGroups.ts`）:

```typescript
interface RecordGroup {
  id: string;
  name: string;
  collapsed: boolean;
  /** 仅空分组使用：null = 列表最前；undefined = 列表末尾；uuid = 该记录所在块之后 */
  anchorUuid?: string | null;
}
```

- 运行时：`workspace.groups` 持有分组定义，记录上只有 `groupId`
- 顺序约定：`records` 数组的顺序就是播放顺序；同组记录在数组里连续，分组表头显示在这段记录之前
- 空分组没有记录可挂靠，用 `anchorUuid` 记住位置；一旦组内有了记录，位置就由记录本身决定（锚点被清掉）

**保存**（`projectFile.ts` + 主进程 IPC）:

| 场景 | 走法 |
| --- | --- |
| 已有 `filePath` | `electronAPI.writeFile(path, text)` → IPC `file:write`，直接覆盖，不弹框 |
| 没有 `filePath` | `electronAPI.saveProjectFile(name, text)` → IPC `dialog:saveProjectFile`，选完路径后记住 |
| 浏览器 / 旧主进程 | `downloadProjectFile()`，用 `<a download>` 下载一份 |

**解析**（`parseProjectText`）:

1. 兼容两种写法：顶层数组，或包一层的 `{ records: [...] }`
2. `normalizeRecords()` 逐条补齐：`dialogue` 缺省字段、各类视觉元素数组、`audioCommands`（后端字段 `audioId` → 前端 `path`，`BGM_ACTIVE`/`SFX_PLAY` 之类别名归一）、大写情绪名 → 前端枚举、非法颜色回退空串、自由文本新字段的默认值
3. `readGroups()` 从记录快照还原分组定义，`keepKnownGroups()` 丢掉找不到定义的 `groupId`（记录变回未分组）
4. 没有有效记录时提示"工程文件里没有找到有效记录"

## 图像处理

### 立绘裁剪 (PortraitPreview)

**路径**: `features/common/components/ResourceManager/tabs/PortraitModal/components/PortraitPreview.tsx`（样式 `AdvancedImageCropper.css`）

- 用 `react-advanced-cropper` 的 `<Cropper>` 实现 1:1 裁剪框，裁剪结果 `{ faceX, faceY, length }` 写回立绘
- `useImageCropper` Hook 负责 `croppedAreaPixels`、图片加载与重置；`useFileSelector` Hook 负责选文件、`blobToBase64`、从文件名识别情绪
- 打开时用默认立绘的裁剪参数**预置**裁剪框（`defaultCoordinates`），保证同一角色不同表情的缩放一致：
  - `length` 存的是**原图像素**，同一角色的立绘可能是 1600×2432、也可能导出了 640×983 的版本，所以换图时要按源图（默认立绘 / 这张立绘自己的旧图）的比例换算到新图上（`resolveCropForNewFile()`），不能照搬像素值
  - 换算要读两边的原图尺寸，所以选完文件先算好裁剪再挂裁剪器（`isPreparingImage`），避免先用旧裁剪框闪一下
- 「裁剪与默认立绘一致」按钮（`defaultCropState` + `defaultPortraitImagePath`）：
  - 目标框由 `features/common/utils/portraitCrop.ts` 的 `resolveDefaultCropRect()` 算出：读默认立绘原图尺寸 → `toCropRatio()` 换成「中心点 + 边长占宽度的比例」→ `resolveCropRatioRect()` 按同样的比例落到当前图上 → 取整 → **夹进当前图片范围**
  - 只有拿不到默认立绘原图尺寸时（图片 404 / 解码失败）才退回按像素照搬，并在裁剪框上方提示用户手动核对
  - 夹过之后必须用裁剪器 `getCoordinates()` 的**实际**坐标回调 `onCropComplete`，不能用入参的原始值 —— 否则保存下来的 `faceX / faceY / length` 会和用户眼前的裁剪框对不上，缩略图也会裁偏
  - 图片还没读进裁剪器时（`getState()` 为 null）不能直接 `setCoordinates`，那会把画布清空、看起来像"点了没反应"；此时先等它就绪（`CROPPER_READY_TIMEOUT_MS`）再补应用
  - 角色没有默认立绘、默认立绘没框过头（`length <= 0`）、或正在编辑的就是默认立绘本身时，按钮**不显示**（没有可对齐的目标，硬套只会把框丢到 (0,0)）
- 缩放倍率由 `PortraitModal/utils/imageUtils.ts` 的 `calculateZoomLevel()` 按裁剪框边长换算（`useImageCropper` 内部保留，裁剪器自己按 `defaultCoordinates` 定位，不再由它驱动）
- **缩放 / 平移立绘时裁剪框跟着立绘走**：`<Cropper transformImageAlgorithm={keepStencilImageRect}>`。
  裁剪器默认把框钉在画面上，滚轮 / 拖动画面只是把立绘塞进框里或从框下滑走（框不再套着同一块脸，
  还会悄悄改掉裁剪值）；这个自定义算法在库算完之后把 `coordinates` 还原成操作前的原图像素矩形 ——
  缩放 / 平移时框跟着一起动，相对位置不变。还原整个 `coordinates` 也顺手修掉了库的
  `moveToPositionRestrictions` 夹取：框被缩放到可见区域外时，一拖画面框就会被拉回区域、相对位置全变。
  只接管"看画面"的缩放 / 平移，拖框改位置或大小仍走库的默认规则（那才是改裁剪区域）
- 保存时用 `createCroppedImage(portraitPreview, croppedAreaPixels)` 在 canvas 上裁出缩略图，再经 `uploadPortraitThumbnail` 上传（原图走 `uploadPortraitFile`），裁剪区域四舍五入后写回 `faceX / faceY / length`
- 缩略图是**覆盖同名文件**的，保存后必须让立绘列表重新取图：`onSave` 走 `CharacterDetailModal.handlePortraitSaved()`，除了更新立绘数据还会 `bumpThumbnailVersions([portraitID])`，列表里的缩略图当场换成新头部的图（不用关掉角色弹窗重新打开；细节见上文「缩略图缓存」）

### 按截图反推裁剪框 (ReferenceCropDialog)

**路径**: `features/common/components/ResourceManager/tabs/PortraitModal/components/ReferenceCropDialog.tsx`（样式 `ReferenceCropDialog.css`；几何内核 `features/common/utils/referenceCrop.ts`；查看视图 `features/common/utils/referenceView.ts`）

入口在「编辑立绘」裁剪框下方：`按截图校准`。选一张 16:9 游戏截图 → 立绘半透明叠在截图上 → 拖动 / 滚轮 / 方向键把立绘缩放到与角色一样大、头部竖直中心对上蓝色靶带的中线 → 写回 `faceX / faceY / length`。

- **只取"缩放比例 + 头部方框中心的竖直位置"**：`length` 由缩放决定，`faceY` 由头部方框中心的竖直位置决定。**水平位置完全不从截图读** —— 原作里角色的左右站位是镜头调度（同一个人这一镜偏左、下一镜偏右，甚至被推到画面边缘），拿它反推会把整个裁剪框带偏（缩略图只剩半张脸、成片里人也偏）。所以：
  - `length = 146.4 / S`
  - `faceY = (108 + 0.8 · (anchorY + adjY) − TY) / S`，`anchorY = 221 + (171 − 身高cm) × 8.333`（向零截断，与 Java 的 `(int)` 一致；8.333 = 成片实测 6.667px/cm ÷ 0.8）
  - `faceX = centerX − length / 2`，`centerX` 取**当前裁剪框的水平中心**（`cropCenterX()`，没有有效裁剪时退化为立绘图片中心）——只按新的 `length` 重新居中，左右位置保持用户已经框好的那个中心
  - 因此角色站在画面哪边都能校准；水平方向拖多远、按多少次方向键，写回的 `faceX` 都不变（有单测钉住）
- **为什么能反推**：用户缩放 = 1 时，立绘在成片里的位置只由 3 个数决定（`CharacterVisual.updatePos()`：`posX = 960 + adjX − faceX · baseScale`、`baseScale = 183 / length`）。头框在成片里恒为 `183 × 0.8 = 146.4` 像素、左上角恒在 `(960, 108 + 0.8 · anchorY)`（场景层 ×0.8 + (192,108)，与 `previewLayout.ts` 的 `SCENE_SCALE` / `SCENE_OFFSET_*` 同源），**与具体裁剪框无关**
- **身高必须填对**：`anchorY` 每差 1cm，成片里的头框上边缘就差 6.67px（8.333 设计像素 ×0.8），表现是 `faceY` 系统性偏移（`length` 不受影响）
- **锚点是"立绘最低能落到哪里"**：`posY = anchorY − faceY · 缩放`，而 `faceY` 是立绘原图内的坐标（夹到 ≥0），所以任何立绘都不会比锚点更靠下。身高锚点一旦偏高，反推出来的 `faceY` 就是负数、被夹成 0，屏幕上的表现是「校准完角色还是偏高」而界面看不出原因 —— 因此这种夹取单独给 `anchorBelow` 提示（"多半是角色身高填得偏高"）。**12px/cm 的老口径就踩过这个坑**：它比原作截帧实测（167/174/180/182cm 四组样本 + 188cm 的《默尔索》帧）陡 44%，171cm 处看不出来，188cm 会高出 50px，校准完全救不回来
- **不做自动图像配准**：真实截图里有对话框、其他角色、压暗与特效，多尺度模板匹配容易给一个"看着差不多"却偏几十像素的结果；人眼对齐一次就有唯一解，而且用户能立刻看出对不对
- **写回必须走裁剪器**：弹窗只把裁剪参数抛给父组件，真正写回用 `PortraitPreview` 暴露的 `PortraitPreviewHandle.applyCropRect()`（`useImperativeHandle`）→ 裁剪器 `setCoordinates` → 回读 `getCoordinates()` 的**实际**坐标回调 `onCropComplete`。否则界面上还停在旧框、保存下来的却是新值（与「裁剪与默认立绘一致」同一条坑）
- **打开时以当前裁剪为初始对齐**（`alignmentFromCrop` + `centerX = cropCenterX(当前裁剪)`），所以什么都不拖直接写回是恒等变换；「恢复当前裁剪」把对齐退回打开时的状态
- 靶带只画**上下两条边 + 中间那条"头部中心"线**，故意不画左右边：画成方框会让人以为必须把角色拖到画面中间
- 截图按宽度铺满 1920，非 16:9 时纵向居中并提示

#### 查看视图：缩放 / 平移（`referenceView.ts`）

舞台上的放大缩小**只是"看"**：`ReferenceView = { scale, panX, panY }`，画在 `.reference-crop-frame` 的
`transform: translate(pan) scale(scale)` 上。截图、立绘、靶带都在这个 frame 里，所以永远同步缩放、保持对齐；
它**不参与**任何反推计算 —— 放大到 400%、平移到角落，写回的 `faceX/faceY/length` 一个字不变（有单测钉住）。

- **比例口径是绝对的**（CSS 像素 / 画面像素）：`100%` = 1 个画面像素对 1 个屏幕像素；「适应窗口」在
  1100px 宽的弹窗里通常是 50%~60%，两者刻意分开，各有一个按钮。
- **边界**：下限 25%（窗口特别小时允许缩到"适应"为止），上限 400% 且至少 4× 适应（`viewScaleBounds()`）。
- **平移夹取**：画面比舞台小就居中，比舞台大就不许露白（`clampViewPan()`）——所以在"适应"状态下拖不动，
  放大后才拖得动，符合直觉。
- **滚轮**：以指针为锚点缩放（`zoomViewAt()`），一帧内的滚轮量先累计再算倍率（rAF 合并），
  所以触控板的小增量不会被吞、快速滚动也不会一次跳到天上去；倍率夹在 `[0.5, 2]`，
  标准鼠标一格 deltaY=100 → 约 ×1.105（`WHEEL_ZOOM_SENSITIVITY`）。
- **按钮 / 键盘**：`−` / `＋` 按 ×1.1 逐级（`VIEW_ZOOM_STEP`）；`+`/`-`/`0`/`1` 快捷键；「适应」「1:1」一键复位。
- **比例输入框**：显示到 0.1 级（`57.3%`），可输入 `150`、`150%`、`1.5x` 三种写法（`parseZoomPercent()`），
  非法输入自动还原；锚点是舞台中心。
- **平移操作**：按住空格 + 拖动，或中键拖动（`cursor` 会变成 grab/grabbing）。
- **校准拖动**：立绘拖动仍以左键为准，位移按 `屏幕像素 ÷ view.scale` 换算成画面像素，
  所以任意缩放级别下都跟手（150% 下拖 150 屏幕像素 = 100 画面像素，有单测）。
- **Alt+滚轮** 缩放立绘（校准）而不是视图；灵敏度与按钮步进见下一节。
- 纯函数单测 `referenceView.test.ts`（22 条：适应/边界/锚点缩放/平移夹取/坐标往返/文字与输入解析/滚轮倍率/
  0.01 级格式与立绘缩放灵敏度）；
  组件测试 `ReferenceCropDialog.test.tsx` 覆盖比例显示与输入、±/1:1/适应、滚轮、中键与空格平移、放大后拖动立绘的坐标换算。

#### 立绘缩放的精度（校准，`referenceCrop.ts` 的 `zoomAlignmentAt()`）

「立绘缩放」与「视图缩放」是两套独立控件：前者改的是对齐的 `scale / x / y`（反推输入，影响裁剪框），
后者只改 `transform`（只影响看）。头部大小要和截图对齐到一两个像素，5% 一档不够，所以：

- **按钮**：`−` / `＋` 默认 **1%** 一档；**Shift** 点按 **5%**；**Alt** 点按 **0.1%**
  （400px 的裁剪框上分别约 4px / 20px / 0.4px）。
- **滚轮**：**Alt+滚轮 0.5%/格**，**Shift+Alt+滚轮 0.1%/格**
  （`WHEEL_PORTRAIT_ZOOM_SENSITIVITY` / `WHEEL_PORTRAIT_ZOOM_FINE_SENSITIVITY`，都在 `referenceView.ts`）。
- **精确输入框**：显示到 **0.01%**（例如 `36.62`），支持输入 `36.62`、`36.62%`、`0.3662x` 三种写法，
  Enter 应用、Esc 放弃；锚点是画面中心。读数栏同时显示 `立绘 36.62%`，与 `视图 50%` 并排。
  控件前的「视图」「立绘」小标签用来区分两组缩放。
- **锚点缩放**：统一走 `zoomAlignmentAt(alignment, nextScale, anchorX, anchorY)` —— 锚点下的那块立绘
  保持不动；`scale` 由 `clampAlignmentScale()` 夹进「头框边长 24~8192px」的合法区间。滚轮也以画面中心
  为锚点（不跟指针），所以缩放对齐时不会顺手把立绘挪走。
- 缩放只影响反推的输入，反推公式与写回路径不变；「左右位置不参与校准」的规则也不变。
- 单测：`referenceCrop.test.ts` 的「立绘缩放（以锚点缩放对齐）」（5 条：锚点不动 / 非中心锚点 /
  NaN 与夹取 / 不可用对齐 / 1% 后 length 400→396）+ `referenceView.test.ts` 的两条
  （0.01 级格式、滚轮灵敏度）+ `ReferenceCropDialog.test.tsx` 的步进与输入框用例。

### 立绘批量操作（立绘列表）

**路径**: `features/common/components/ResourceManager/tabs/CharacterDetailModal.tsx`（界面 `CharacterDetailModal/PortraitsSection.tsx`，纯逻辑 `features/common/utils/portraitBatch.ts`）

立绘列表标题行右侧三个按钮：`与默认立绘裁剪一致` / `批量导入立绘` / `添加立绘`；批量操作进行中按钮全部禁用，并显示 `正在应用裁剪 2/5…` 这类进度条，结束后在列表上方留一条结果提示（成功/警告/错误三种配色）。

- **与默认立绘裁剪一致**（`handleApplyDefaultCropToAll`）
  - 按**比例**套用，不再照搬像素：先 `loadPortraitImageSize()` 读默认立绘自己的原图尺寸，把它的 `{ faceX, faceY, length }` 换成「中心点 + 边长占宽度的比例」，逐张按各自原图尺寸换算后**夹进图片**，写回**夹取后的实际坐标**
  - 目标集合由 `collectCropUpdateTargets()` 挑：排除默认立绘本身；**不**再按像素判断"已经一致"（比例换算后同一组像素值在不同尺寸的原图上并不等价），是否真的需要改在执行时逐张比较（`isSameCrop()`），一致就跳过、不重复重生成缩略图
  - 点一下先读默认立绘尺寸、再 `window.confirm` 确认（说明是"按比例"还是"按像素"），然后逐张：读原图拿 `naturalWidth / naturalHeight` → `resolveDefaultCropRect({ crop, sourceImageSize, imageSize })` → 用**夹取后的实际坐标**写回立绘 → 用 `createCroppedImageFromElement()` 在同一个 `<img>` 上重生成缩略图并 `uploadPortraitThumbnail` 上传
  - 原图加载失败时退化成"照搬像素值"，缩略图失败只记数并在结果提示里说明，不阻断整批
  - 缩略图文件名固定（`thumbnail_{portraitId}.png`），后端只覆盖内容、不改路径，所以列表靠 `thumbnailVersions`（立绘ID → 代次）让 `PortraitThumbnail` 拼 `?t=` 重新取图；只给**这次真的重算过缩略图**的那几张 +1，其它立绘的 `<img>` 不动
  - 只改前端状态，仍需点角色弹窗右上角「保存」才写数据库
- **批量导入立绘**（`handleBatchImportPortraits`）
  - 选文件：Electron 走主进程多选对话框（`dialog:openImageFiles`，preload 暴露 `openImageFiles`）；浏览器开发模式退化成 `<input type="file" multiple>`
  - 逐张：用 `URL.createObjectURL(file)` 读尺寸 → 有可用的默认立绘就**按它的比例**套用裁剪（先读默认立绘原图尺寸，再按各自原图尺寸换算并夹进图片），没有则用 `(0,0,100)` 兜底 → `uploadPortraitFile` 落原图 → 生成并上传缩略图 → `buildImportedPortrait()` 组装立绘（情绪按文件名识别，中文/英文关键词都支持）
  - 和角色里已有立绘**同名**的文件直接跳过（`hasPortraitName()`），避免同一个文件夹导入两次变成两倍
  - 新角色会先静默保存再上传（`ensureCharacterPersisted()`），否则后端会报"角色不存在"；选文件阶段就取消则不会保存角色
- 纯函数（`portraitBatch.ts` / `portraitCrop.ts`）都有单测：`portraitBatch.test.ts`、`portraitCrop.test.ts`

`AppConfig.designCanvas = { width: 1920, height: 1080 }`，必须与后端 `ProjectConfig.VIDEO_WIDTH / VIDEO_HEIGHT` 一致。

### 预览舞台与几何（interactive preview，P0）

**路径**: `features/record/preview/`

预览图是后端渲染的**栅格图**，没有 DOM 结构，点不到任何东西。要让预览能点、能拖、以后还要能设摄像机，
就必须知道每个元素在图上的矩形——`previewLayout.ts` 就是干这个的：用与后端**逐行相同**的公式，把记录换算成像素矩形。

**三层坐标系**（与后端渲染管线一一对应，改公式前先看 `RenderOfImage.renderPre`）:

```
世界空间（可以远大于 1920×1080）      背景 / 立绘 / 临时图片  ← previewLayout 算的就是这里的矩形
      │ worldToScene：摄像机取景（identity 时是恒等变换）
场景画布 1920×1080
      │ ×0.8 并偏移 (192,108)          ← RenderOfImage.PLOT_SCENE_SCALE
设计画布 1920×1080
      │ 边框 / 对话框 / 名片 / 地点牌 / 台词（**不受摄像机影响**）
      │ ×(W/1920, H/1080)
预览图 / 视频帧 W×H
```

| 文件 | 作用 |
| --- | --- |
| `previewLayout.ts` | 纯函数几何：`buildPreviewGeometry()` 返回全部图层（`outRect` 已含摄像机 + 0.8 + 输出缩放）、`worldRef`（世界参考框）、`worldBox`（含一帧余地）、`missingSizes`；另有 `layerAt` / `layersAt` 命中检测、`clampCamera` / `worldToScene` 留给摄像机模式 |
| `previewAssets.ts` | 图层 key（`background:0` / `character:1` / `tempImage:0`）→ 原图地址；立绘**必须**用 `buildPortraitImageUrl`（缩略图是裁剪后的，宽高比不对） |
| `useImageSizes.ts` | 预加载原图尺寸（模块级缓存，跨记录复用；失败不重试，避免每次渲染都发请求） |
| `useElementSize.ts` | 量预览容器像素。舞台的**位置与大小都用 px 算**（不依赖 CSS `aspect-ratio` 在 flex 里的表现），再让叠层用百分比铺满舞台，保证"舞台 = 图片 = 百分比坐标系" |
| `PreviewSceneLayer.tsx` | DOM 场景层：按几何把背景/立绘/临时图片重绘一遍（定位全用百分比） |
| `PreviewHitLayer.tsx` | 热区层：每个图层一个透明 `<button>`，点击 → 选中 + 切页签；拖动 → 改位置；点空白取消选中 |
| `previewTargets.ts` | 纯函数映射：图层种类 → 页签 + 定位目标（`PropertyFocusRequest`）；`keepsActiveTabOnSelect()` 决定「摄像机」页签下点元素只选中、**不切页签**（切走会卸载世界视图、打断正在拖的手势） |

| `useCameraEditor.ts` | 摄像机编辑状态（唯一真源，由 RecordEditor 持有）：正在编辑哪一帧、拖动工具、视图缩放/平移、运镜时长草稿、播放头；`applyEditing` / `setEasing` / `resetCamera` 负责写回记录。页签与世界视图共用这一份 |
| `useCameraPlayback.ts` | 运镜播放头：按帧推进 `min(moveFrames, 记录时长)` 帧，停在终点 |
| `hitCycle.ts` | 纯函数：重叠区域重复点击时"循环下钻"选下一层 |

**请求节奏**（`RecordPreview.tsx`）:

- **防抖 150ms**：连续编辑（打字 / 拖滑杆 / 以后的拖拽）只发最后一次渲染请求，请求量降到原来的几十分之一
- **旧图不卸载**：请求期间只显示右上角「渲染中…」，避免每改一个字就闪一下
- **blob URL 延迟释放**：新图挂到 DOM 之后才 `revokeObjectURL` 旧图（以前是先 revoke 再请求，画面会白一下）

**对位自检（怎么验收几何是对的）**:

预览舞台右下角两个很淡的小开关：

| 开关 | 效果 | 验收标准 |
| --- | --- | --- |
| `▦ 框` | 把每个图层的矩形画成彩色框（绿=背景、黄=立绘、青=临时图片、紫=对话框、橙=角色名片、蓝=地点牌） | 框应与画面里的同名元素**边缘重合** |
| `◧ 场景` | 栅格图压到 35%，用 DOM 场景层按几何重绘背景/立绘/临时图片 | 两层应**完全重合**（有位移会立刻看到重影） |

> 2026-10-21 用真实素材做过一次回归：1920×1080 下立绘轮廓放大 3 倍做 50% 混合，边缘完全清晰无重影（误差 ≤1px）；
> 背景区域的亮度差异来自后端 `buildBorderMask()` 生成的暗角遮罩与双三次重采样，属于**像素近似**而非位置偏差。

**UI 图层的三条约定（台词 / 角色名片 / 地点牌）**:

- **台词不单独成框**：文字画在对话框上，所以它没有独立热区；点击对话框 == 点击台词。
- **角色名片只在"角色说话"时出现**，层级**高于对话框**（`z`: 对话框 300 < 名片 305 < 地点牌 310）。
  重叠区域点击归名片；名片之外仍归对话框。判定规则镜像后端的 `addUILayers`：
  自由文本不画、旁白不画、`speakerC` 是 narrator 占位不画、只有手填名字（临时说话人）也画。
- **旁白**（`speakerName === "旁白"`）：只有对话框，没有名片。

**点击命中 → 页签与属性定位（P1）**:

预览图上盖着一层**透明按钮**（`PreviewHitLayer.tsx`）：每个图层一个 `<button>`，位置/尺寸用百分比，
`z-index` 取图层的 `z`——"点到谁"直接交给浏览器层叠规则，与后端绘制顺序天然一致，不需要手写命中算法。
附带好处：Tab 可以逐个走一遍、Enter/Space 等同点击，`aria-label` 就是元素名。

| 点中的东西 | 切到的页签 | 面板里定位到 | 视觉 |
| --- | --- | --- | --- |
| 背景 | 🖼️ 背景 | 第 i 张背景卡片 | 滚到卡片 + 闪蓝框 1.6s |
| 立绘 | 👤 立绘 | 第 i 个角色卡片 | 同上 |
| 临时图片 | 🧩 临时图片（**不是**立绘页签） | 第 i 张临时图片卡片 | 同上 |
| 对话框（含台词） | 📝 文本 | 「对话内容」 | 同上 |
| 角色名片 | 📝 文本 | 「说话人」 | 同上 |
| 地点牌 | 📝 文本 | 「场景」 | 同上 |
| 空白（黑边/无元素处） | 不变 | — | 取消选中 |
| *（在「摄像机」页签的世界视图里）* | **不切页签** | — | 只选中（可继续拖动）；世界视图就是这个页签的画布 |

- 映射规则集中在 `previewTargets.ts`（纯函数 + 单测），`RecordEditor` 只负责
  「记选中态 → 切页签 → 下发一次定位请求」；「摄像机」页签由 `keepsActiveTabOnSelect()` 拦下，
  切页签会卸载世界视图、把正在拖的手势打断在半路；
- 定位请求带 `nonce`（时间戳），**同一个元素连点两次也会重新滚动 + 闪烁**；
- 选中态由 `RecordEditor` 持有，**切换记录时自动清空**，避免选中框留在别的记录上；
- 悬停显示淡青色框、选中显示实线框、键盘聚焦显示黄色外框，三种状态互不混淆；
- 属性面板的高亮样式是 `RecordEditor.css` 的 `.property-focus-flash`，与「文本 → 全局显示速度」的
  跳转高亮同一套视觉；时长与 `preview/useFocusFlash.ts` 的 `PROPERTY_FOCUS_FLASH_MS`（1600ms）对齐。

**重叠元素「循环下钻」（`hitCycle.ts`）**:

多个立绘 / 临时图片叠在一起时，只选最上层会让下面那张永远点不到，所以同一片重叠区域支持重复点击逐层下钻：

| 情况 | 行为 |
| --- | --- |
| 首次点击重叠区域 | 选中最上层 |
| 在同一重叠区域再点 | 每次往下钻一层 |
| 已钻到最底层再点 | 回到最上层（循环） |
| 点另一片命中集合不同的区域 | 按新区域的规则命中，循环从该区域最上层重新开始 |
| 点空白 | 取消选中，并清空循环记忆 |

实现要点：

- **命中集合** = 该点命中的全部图层，按 `z` 从高到低（`layersAt` 已排序）；判定是纯函数
  `resolveCycledHit(layers, point, previous)`，`hitCycle.test.ts` 覆盖了钻到底回顶层、换区域重置、
  空白清空、`z` 序变化视为新集合等情况；
- **点击必须由外层容器统一处理**：DOM 事件只会落在最上层那个按钮上，容器才知道完整命中集合，
  所以鼠标点击冒泡到 `.preview-hit-layer` 上，由它把 `clientX/Y` 按舞台尺寸换算成预览图像素再判定；
- **键盘不参与循环**：`event.detail === 0` 的 click（Enter/Space）直接选中该按钮对应的元素，
  保证 Tab 走查是"一个焦点一个确定结果"；
- **循环记忆跟着选中态走**：外部把选中清成 `null`（切记录 / 点空白）时，组件内的循环记忆一并作废，
  否则下一次点同一片重叠区会从"上一层的下一层"接着走。

**拖动元素改位置（P2，`previewDrag.ts`）**:

在预览里直接拖立绘 / 背景 / 临时图片，写回记录里对应的位置字段：

| 图层 | 写入字段 | 语义 |
| --- | --- | --- |
| 立绘 | `adjX` / `adjY` | 相对身高锚点的偏移（`posX/posY` 是后端派生值，前端不写） |
| 背景 | `posX` / `posY` | 背景中心相对画面中心的偏移 |
| 临时图片 | `posX` / `posY` | 图片左上角的绝对坐标 |

- 位移换算：`设计像素 = CSS 像素 × 1920 / 舞台宽 / (0.8 × 相机zoom)`（`worldDeltaFromStage`）；
- 越过 3px 才进入拖拽（否则按点击处理，不会点一下就把元素挪 1px）；拖动即选中，属性面板同步切页签、数值实时跟着变；
- 位移用 `requestAnimationFrame` 合并，一帧最多回写一次；**Esc 取消并还原到起点**，Shift 锁定单轴；
- **拖拽期间隐藏栅格图、改用 DOM 场景层**（栅格图一次要几十上百毫秒，跟不上鼠标），并**暂停预览图请求**，松手后才补一张；
- DOM 场景层为此要画出整幅画面：背景/立绘/临时图片 → **边框暗角（CSS 复刻）** → 对话框/地点牌（静态 PNG）。
  **缺口是「角色名片」**——它由后端按说话人实时生成，前端没有对应图片，所以拖动的那一两秒里名片（以及台词文字）会暂时消失，松手后恢复。
- **边框不是素材**：后端用 `RenderOfImage.buildBorderMask()` 现画一张 1920×1080 的黑色渐隐遮罩
  （`alpha(d) = 1/(1+(d/81.25)^3)`，纵向半衰 63.75，中心全透明），画在场景画布 (0,0) 再随 0.8 一起缩放。
  DOM 场景层用四条 `linear-gradient` 复刻它（`preview.css` 的 `.preview-scene-border`），
  **不要去读 `assets/ui/border.png`**——那是另一张 1536×864 的旧素材，贴在场景层上会出现一个错位的小黑框。

**撤销 / 重做（Ctrl+Z / Ctrl+Y，`recordHistory.ts`）**:

- 两个栈存的是**整份工程快照**（记录数组 + 分组定义），每次改动前压一份，最多 50 步；
- **连续编辑合并成一步**：500ms 窗口内的改动只保留最早那份快照（打字、拖滑杆不会变成"逐字符撤销"）；
  结构性改动（增删记录 / 拖排序 / 分组操作 / 全局文字速度）各自独立成一步；
- **一次拖动算一步**：拖动开始时压栈，拖动过程中挂起压栈（否则每帧都会入栈）；
  拖到一半按 Esc 取消时会顺手弹掉那一份（已经手动还原，留着会变成空操作）；
- **重做**：每次撤销都会把"撤销之前的样子"推进重做栈；重做时把当前状态放回撤销栈，所以可以来回切。
  **任何新改动都会清空重做栈**（撤销后又改了东西，说明已经分叉，前进就没有意义了）；
- 撤销/重做后都**强制预览图跳过后端磁盘缓存**（`refreshToken` prop）：两者都是把记录改成旧内容，
  后端缓存按 `uuid` 存，直接用缓存会停在改之前的画面；
- 快捷键：`Ctrl/⌘ + Z` 撤销、`Ctrl + Y`（或 `Ctrl/⌘ + Shift + Z`）重做，
  捕获阶段注册，避免被输入框的原生撤销/重做抢走；栈空时给一条 toast 提示。

### 摄像机（C1）

**数据模型**：`Record.camera?: RecordCamera { centerX, centerY, zoom }`，一记录一个；

- 缺省 / 恒等（`960, 540, 1`）= 加摄像机之前的效果，旧工程没有这个字段照常渲染，**逐像素不变**；
- 归一化三处一致（`projectFile.normalizeCamera` / `cameraView.normalizeCamera` / 后端 `Camera.getZoomFactor`）：
  `zoom` 收敛到 `[0.5, 4]`，`zoom <= 0` 当 1，非法中心回落画布中心；
- 写工程文件时恒等镜头直接不写（`undefined`），避免每个旧记录都多一个空镜头；
- 后端 `Record` 的 `camera` 从 `@JsonIgnore` 改成 `@JsonProperty` —— 导出视频时记录是请求体，
  不带镜头就等于白拖；`PREVIEW_CACHE_VERSION` 因此升到 `v11`（旧缓存里没有按镜头渲的图）。

**坐标系**（改公式必须两处同步）：

```
世界空间（可远大于 1920×1080）      背景 / 立绘 / 临时图片 的坐标
      │  scene = (world - center) * zoom + (960, 540)      ← Camera.screenX/screenY
      ▼
场景画布 1920×1080（= 取景框）      → ×0.8 + (192,108) → 设计画布 1920×1080 → 输出 W×H
```

只有**场景层**（背景 / 立绘 / 临时图片）过镜头；边框暗角、对话框、角色名片、地点牌、台词都在设计画布上
直接画，**不受镜头影响**。后端在 `Camera.isIdentity()` 时短路，完全不走换算，所以旧工程不会因为
多了一次取整而差一像素。

**界面：一个页签 + 一块画布**

从前镜头控件浮在预览画面上的工具条里（遮画面、和成片抢位置，而且不算"属性"）。现在：

- **「摄像机」页签**（`properties/CameraProperties.tsx`）= 全部控件：状态摘要、编辑起点/终点、中心读数、
  缩放（± 与滑杆）、缓动、运镜时长、▶ 播放 / 复位镜头 / 适配视图 / 铺满背景、拖动工具；
- **世界视图**（`preview/CameraModeView.tsx`）= 画布：背景/立绘/临时图片铺在可缩放画布上 + 16:9 取景框，
  框外压暗；`PreviewHitLayer` 只在工具=移元素时挂上。**画布上没有任何浮动控件**；
- **预览模式由页签决定**：`RecordEditor` 传 `viewMode={activePropertyTab === "camera" ? "camera" : "effect"}`，
  进页签 = 世界视图，离开 = 后端渲的成片（预览顶部的 🖼/🎥 只是状态标签，不再可点）；
- **播放按钮在两种视图里都有**：最终效果里播的是成片 DOM 近似；世界视图里点 ▶ 会**临时切到成片预览**
  （`previewingFromCamera`，状态标签变成"🖼 成片预览中"），播完/停止后自动回到世界视图
  ——这样在「摄像机」页签里构图时不用来回切页签就能确认成片效果；
- **两份界面共用一份状态**：`useCameraEditor` 由 RecordEditor 持有一份，向页签与世界视图各发一份。
  所以"页签里选终点、画布里拖的也是终点"，反过来也一样；切换页签不会丢"编辑的是哪一帧 / 视图缩放"。

**交互**（`CameraModeView.tsx`，世界视图）：

| 操作 | 作用 |
| --- | --- |
| 拖动（工具=移镜，默认） | 移动镜头；取景框四条边是永远可拖的手柄 |
| 按住 Alt | 临时反转当前工具（移镜 ⇄ 移元素） |
| 拖动（工具=移元素） | 拖背景/立绘/临时图片，走 P2 那套 `writeLayerPosition` |
| 滚轮 | 推拉镜头，以指针处的世界点为锚（`zoomCameraAt`） |
| Ctrl/⌘ + 滚轮 | 缩放**视图**（只看近看远，不改镜头，`zoomViewAt`） |
| 空格 + 拖动 | 平移视图 |
| F / 0 | 适配视图 / 镜头复位（与页签里的按钮等价） |

- **镜头 vs 视图**是两套缩放：镜头进记录、影响成片；视图只是编辑时的显示，不进记录；
- **摄像机页签下点中元素只选中、不切页签**（`previewTargets.keepsActiveTabOnSelect`）：
  世界视图就挂在这个页签上，切走会把它卸载、正在拖的手势断在半路（`PreviewHitLayer` 收不到 pointerup）。
  要看/改元素属性由用户自己切到「立绘」「临时图片」「背景」页签；
- 视图"适配"以**世界参考框 +8% 边距**为基准（世界框含一帧余地，直接适配会让内容只占屏幕 1/3）；
- 世界边界：参考框 = 背景归位框 ∪ 画布（**不跟随背景 posX/posY**），世界框 = 参考框每边再留一个取景框；
  镜头被 `clampCamera` 夹在世界框里 → 最多摇到「世界完全不在画面里」；
- **铺满背景**（按钮在页签里）：后端背景是 contain，30:9 横长条在 scale=1 时只画 1920×576、上下留黑、
  世界也只有画布大、镜头无处可摇。按 `coverScaleForBackground` 算出"刚好盖住当前取景框"的倍数：
  `max(1, 取景框宽/drawW₁, 取景框高/drawH₁)` —— **只放大、不缩小、不拉伸、不改 posX/posY**，
  只作用在**最上层**那张拿得到原图尺寸的背景（下层被盖住，放大了也看不见）；
  公式假设「背景中心 = 画布中心 = 取景框中心」，所以镜头摇开或背景有偏移时会把倍数算少（有意保留的近似）；
- **背景 scale 上限是 4.0**（立绘/临时图片仍是 3.0）：9:16 的竖图要盖住 16:9 取景框约需 3.16 倍，
  卡在 3.0 会差 100 多像素铺不满。前端 `visualCoordinates.MAX_BACKGROUND_SCALE` 与
  后端 `BackgroundVisual.MAX_SCALE` 必须同步（实测 4.6 会渲出与 4.0 完全相同的图，说明夹取生效）；
- 世界视图下**不发预览图请求**（镜头一动记录就变，每动一下都重渲纯属浪费），切回最终效果才补一张；
- 离开「摄像机」页签时**停掉运镜播放**（播放头在编辑器这一层，不停会空转 setState）；
- 移镜产生的连续改动走 `updateRecord` 的 500ms 合并，所以一次拖动通常是 1~2 步撤销。

**验证**：`cameraView.test.ts` 18 条（归一化 / 取景框 / 视图变换往返 / 移镜夹取 / 推拉锚点 / 视图缩放锚点 /
铺满倍数）；后端用「同一记录渲两次，一张恒等一张带镜头，再按 `P = (W-center)*zoom + 画布中心` 采样比较」
核对过 —— **注意取景框是场景画布、再乘 0.8** 才到成片，所以镜头的 440px 平移在成片上是 352px。

### 起止镜头（C2）

一条记录可以有两个镜头：起点（`centerX/centerY/zoom`）和终点（`to`，形状相同），中间用 `easing` 过渡。
没有 `to`（或 `to` 与起点差不到半像素）= 静止镜头，与 C1 完全一样。

- **数据**：`RecordCamera { centerX, centerY, zoom, to?: {...}, easing?: "linear"|"easeIn"|"easeOut"|"easeInOut" }`；
  `projectFile.normalizeCamera` 把 `to` 一起归一化，恒等且无动画才整体丢掉；
- **缓动**：三次曲线 `easeIn = t³`、`easeOut = 1-(1-t)³`、`easeInOut` 分段。前端
  `cameraView.easeProgress` 与后端 `Camera.ease` **必须逐字一致**，否则 DOM 播放和成片对不上
  （两边各有单测钉住同一组数值）。**缺省是「慢出」（`easeOut`）**：
  `DEFAULT_CAMERA_EASING` 与后端 `Camera.easing` 的字段初值都是 `easeOut`，
  所以"拖一下自动生成终点"时默认就是起速快、收尾慢；老数据里显式写了 `linear` 的保持匀速；
- **编辑**：「摄像机」页签的「◆ 起点 / ◇ 终点」决定拖框、滚轮推拉、±/滑杆改的是哪一帧；选中一帧时，
  另一帧画成**虚线虚影**，一眼看出镜头会往哪走。终点缺省时与起点重合，**改一下（拖框/推拉/滑杆）就自动生成 `to`**；
- **播放**：
  - 「摄像机」页签的「▶ 播放」——取景框按记录时长在起点/终点之间移动（世界视图里看构图怎么走）；
  - 最终效果模式「▶ 播放」（预览顶部的按钮）——隐藏栅格图、用 DOM 场景层按插值镜头**每帧重算几何**
    （`buildPreviewGeometry` 的 camera 参数换成 `cameraAt(camera, t)`），所以能真的看到推拉/摇镜。
    台词不参与动画（DOM 层画不出文字动画）；
  - **DOM 场景层必须裁到「场景框」**：成片里场景只占设计画布中间 80%（`0.8` 缩放 + `(192,108)` 偏移），
    四周一圈纯黑；镜头一摇/一推，背景会被画到 1920×1080 之外，后端在合成场景画布时就裁掉了。
    `PreviewSceneLayer` 因此有 `clipRect` 参数（最终效果传 `sceneToOutput({0,0,1920,1080})`，
    用 `clip-path: inset(...)` 裁；世界视图不传——要看全图）。漏了这一步的表现是
    "播放时黑边没了、背景铺满整个画布"；
  - **裁剪只作用于世界层，图层顺序是：世界层 → 边框暗角 → UI**。只有背景/立绘/临时图片带
    `clipWithScene`（进裁剪容器），边框暗角与对话框/地点牌留在外面——成片里 UI 是画在设计画布上的，
    对话框底边（1080）本来就压在下方的黑边上（场景框底边 972），跟着裁会被黑框咬掉一截，
    看起来就是"黑框盖住了 UI"；
  - 时长 = 运镜帧数 / 30（见下节），播放时暂停预览图请求；
- **出片**：`RenderOfVideo` 在镜头会动时**逐帧重渲场景层**（`renderStaticLayer(..., Camera.at(camera, t))`，
  `t = 帧序/(总帧-1)`），静态层缓存与"定格复用"在这种记录上自动失效；`renderLastFrame`（交叉溶解用）
  取 `t = 1` 的最后一帧。预览图接口始终用 `t = 0`（起点）。

**性能提醒**：镜头会动的记录，导出耗时 ≈ 帧数 × 单帧场景渲染时间（静止镜头只渲一次）。
没有做"按镜头路径最宽取景预渲一张大图再裁"的优化：那要开更大的画布，内存与重采样误差都不划算。

**运镜时长（`moveFrames`，默认 24 帧）**：

- 字段：`RecordCamera.moveFrames`（整数，最小 1，缺省 24）。只有"有终点"时才有意义；
- 语义：**在 moveFrames 帧内从起点走到终点，之后停住**等这条记录剩下的时间播完。
  进度公式三处共用：`cameraView.cameraProgressOf(frame, moveFrames)` 与后端 `Camera.progressAt(frame, moveFrames)` 完全同构
  —— `frame / (moveFrames - 1)` 夹到 `[0, 1]`，`moveFrames = 1` 时第 1 帧即到终点；
- UI：「摄像机」页签的「运镜 __ 帧」数字框（只在有终点时出现），改完立刻写回记录（带草稿态，
  失焦回落真实值，避免输入过程中被 1 顶掉）；
- 播放：「摄像机」页签的「▶ 播放」只播 `min(moveFrames, 记录时长)` 帧，
  所以**预览时长 = 成片里运镜的时长**，不会因为台词长而拖成十几秒；
- 导出：`RenderOfVideo` 用同一个 `Camera.progressAt`，超过 moveFrames 的帧保持终点镜头。

**新建记录继承镜头（点「+」）**：

新记录的摄像机**起点** = 上一条的**终点**（`cameraKeyframe(prev.camera, "end")`：
有运镜取终点，没有运镜取它当前镜头），这样两条记录之间镜头不会跳。
上一条缺失 / 没有镜头 / 恒等时留空（= 默认位置），不阻塞新建。

**最终效果播放时的遮罩**：

播放中给预览容器加 `.is-playing`（`background-color: #000`），画布以外的区域一律纯黑。
舞台的位置与尺寸完全不变（仍是按视频比例算好的 `left/top/width/height`），只是容器底色变了，
所以不会因为"加一层黑底"导致布局抖动。

**验证**：`CameraTest`（5 条：恒等/动画判定、端点插值、三调缓动、缓动后的中间帧、两端 zoom 夹取）；
`cameraView.test.ts` 追加 8 条（缓动曲线、`cameraAt`、`cameraKeyframe`/`withKeyframe`、归一化保留 `to`）；
端到端实测：同一记录导两次（640×360、4 秒），静止镜头 24KB、动画镜头 **943KB**（38 倍，
说明每帧画面都不同）；从动画 mp4 抽首尾帧比对，末帧确实是"2 倍放大 + 摇到右侧"而 UI 纹丝不动。

**已知边界**:

- DOM 场景层是"几何准确、像素近似"：不做后端的双三次重采样，所以逐像素不会与栅格图完全相等
  （边框暗角与对话框/地点牌已补进场景层，切换时不会突然变亮）。
- 摇镜播放（最终效果模式的 ▶）只动**画面**：台词、角色名片不参与 DOM 动画（它们只存在于栅格图里），
  要看成片效果得导出，或到「摄像机」页签的世界视图里对构图。
- 镜头动画只有一条「起点 → 终点 + 缓动」，没有多关键帧 / 定格 / 曲线编辑器；要更细的分镜得拆成多条记录。
- 角色名片的矩形用**固定值**（后端 `(-26,789) ×0.28`，裁剪后约 1275×528 → 绘制 357×148）：名片由后端按
  「名字 + 阵营 + 两个颜色」现渲染并按内容裁剪，实测不同角色宽度只差 1~3px，所以不做运行时测量；
  `buildPreviewGeometry` 仍留了 `namePlateSize` 入参，将来要做像素级精确时可接后端名片原图尺寸。
- 自由文本 + 隐藏 UI 时**既没有对话框也没有名片**，因此这类记录暂时没有可点击的文字热区（后续如需要再单独约定）。
- 立绘/背景/临时图片的公式镜像自 `CharacterVisual.updatePos()` 与 `BackgroundVisual.getDrawBounds()`；
  这些常量与公式改动时必须同步 `previewLayout.ts`，否则热区会与画面错位（调试叠框能立刻看出来）。
- 单测：`previewLayout.test.ts`（几何数值全部按后端公式手算，后端一改公式这组用例就会红）。

### 摄像机预设（C3）

**路径**: 注册表 `features/record/preview/cameraPresets.ts`，面板 `features/record/properties/CameraPresets.tsx`（挂在「摄像机」页签内），求值 `features/record/preview/cameraShake.ts`

镜头层的**动态效果**（第一个是镜头摇动）统一放在「摄像机 → 预设」区块，与「运镜」并列：

| 预设 | 序列化标识（`record.effects[].type`） | 参数 | 求值 |
| --- | --- | --- | --- |
| 镜头摇动 | `CAMERA_SHAKE` | `amplitude`（屏幕像素，缺省 12）、`periodFrames`（帧，缺省 5）、`durationFrames`（持续帧数，缺省 0 = 整条记录）、`fadeInFrames`（渐入，缺省 0）、`fadeOutFrames`（渐出，缺省 0） | `cameraShake.ts`（与后端 `CameraShake` 逐行对应） |

**时间包络（持续时长 / 渐入 / 渐出）**——前后端必须逐字一致：

```
end   = durationFrames > 0 ? min(durationFrames, 记录总帧数) : 记录总帧数
tIn   = fadeInFrames  > 0 ? clamp(f / fadeInFrames, 0, 1) : 1
tOut  = fadeOutFrames > 0 ? clamp((end − f) / fadeOutFrames, 0, 1) : 1
env   = min(tIn, tOut)                        // f ≥ end 为 0
dx    = amplitude · sin(2πf/period) · env
dy    = amplitude · 0.45 · sin(2πf/(period·0.73)) · env
```

- 三个参数缺省都是 0（整条记录 / 不渐入 / 不渐出），所以**没有这三个字段的旧工程行为不变**；
- `end` 取"持续时长"与"记录总帧数"的较小值，渐出因此永远落在记录内部；预览传
  `playback.totalFrames`（后端准数），导出传 `requiredFrames`（`RecordDurationCalculator`）；
- 不知道记录总长且没设持续时长时 `end` 为无穷远：此时**没有渐出**（没有参照点，前后端同一条规则）；
- 预览的 `f` 可以是小数（播放头按浮点帧推进），导出是整数帧 —— 公式对两者都成立。

**导出侧的一个修正**：`RenderOfVideo` 原来的逐帧渲染条件只有"镜头会动 / 立绘动画"，
**只开了摇动的记录会被当成静止画面整段复用同一张底图**（导出看不到晃）。现在
`sceneChanges` 把 `CameraShake.isActive(record)` 也算进去，并给 `CameraShake.apply` 传总帧数。

**面板上的参数约定**：`CameraPresetParam.min` 是"有效下界"——记录里的值**小于 `min`** 时按
"未设置"回落 `defaultValue`。所以"渐入 0 帧 / 渐出 0 帧 / 持续 0 帧"都填 `min: 0`（0 是合法值），
而 `amplitude` / `periodFrames` 这种必须为正的参数 `min: 1`。

**结构（注册表驱动，面板不认识具体类型）**:

- `CameraPresetDefinition`：`type`（= 后端 `EffectVisual.TYPE_*`，**不能随便改**）、`label`、`emoji`、
  `description`、可选的 `group`（面板自动分节）、`params[]`（`key` / `label` / `unit` / `min` / `max` /
  `defaultValue` / `integer` / `hint`）；
- 面板把 `CAMERA_PRESETS` 渲染成"分组 → 卡片 → 参数行"，**没有任何按类型分支的代码**：
  新增一种预设只是往数组里追加一条定义（需要分组就填 `group`），布局骨架不用动；
- 通用读写函数同样与类型无关：`presetEntryOf` / `isPresetEnabled` / `togglePresetEffect` /
  `withPresetParam` / `presetParamValue` / `groupPresets`（都有单测，且用"假预设"验证过不硬编码）；
- 自适应：所有行都是 flex + wrap，属性栏拖到最窄（300px）时参数行整体换行，不会被裁掉；
  卡片宽度跟随面板，说明文字自动折行。

**数据与兼容（只搬 UI，不动存储格式）**:

- 开关与参数仍然写在 `record.effects`：一条
  `{ type: "CAMERA_SHAKE", enabled, amplitude?, periodFrames?, durationFrames?, fadeInFrames?, fadeOutFrames? }`
  ——前两个参数与迁移前「特效」页签里写的**逐字节一致**，后三个是这次新增的可选字段（缺省 0），
  `projectFile` 原样透传，所以**旧工程不需要迁移脚本**：打开后照样是勾着的，导出也照样生效；
- 勾选写回 `{ type, enabled: true }`（不带参数），参数只在用户改过时才写进去；取消勾选 = 删掉这一条
  （沿用迁移前的语义，不会留下 `enabled:false` 的残留）；
- 唯一新增的兼容逻辑是**类型比较忽略大小写**（`preview/effectType.ts` 的 `matchesEffectType`）：
  后端 `EffectVisual.isEnabledType` 用的是 `equalsIgnoreCase`，前端跟上，手写/旧版工程里的
  `camera_shake` 也能被认出来，不会出现"后端在晃、面板没勾上"；
- 「特效」页签只保留三种起始转场，底部留一句"镜头摇动在「摄像机 → 预设」"的指路说明（不是开关）。

### 镜头自动跟随说话人（C4）

**路径**: 纯运算 `features/record/preview/cameraFollow.ts`；开关在「摄像机」页签最下面的
「构图辅助」区块（`properties/CameraProperties.tsx`，勾一次就一直用，所以不占第一屏的常用控件）；
接线在 `RecordEditor.updateRecord()`；设置项 `projectSettings.cameraFollowSpeaker`
（**工程全局**，缺省关，随其它工程设置进 localStorage —— 控件在按记录的页签里，但作用域是整个工程）

**为什么接在 `updateRecord`**：这个写入口覆盖"预览里拖立绘 / 「立绘」页签推滑杆 / 「文本」页签换说话人"
全部路径，而且**全工程只有这一处会动镜头**。触发与否用"改动前 vs 改动后"的记录做差
（`followTriggerOf`）判断：

- `speakerSignature` 变了（`speakerC[0].characterID` / 手填名字 / 旁白 ⇄ 自由文本）= **切换说话人**；
- 同一位说话人的 `characterGeometrySignature`（`characterLayout` 的 x / y / renderScale）变了 = **移动立绘**
  （位置、用户缩放、头部裁剪框都算；压暗 / 动画装备不算）；
- 其余改动（台词、背景、临时图片、**镜头本身**）一律不触发。所以**手动改镜头永远优先**：
  它走 `updateCamera` → `updateRecord(只改了 camera)`，不满足触发时机，不会被自动逻辑覆盖；
- 新增 / 删除说话人的立绘不算"移动"（需求只列了移动与切换），此时返回 `null`。

**算出来的镜头**（`autoFollowSpeaker`，返回 `{ record, applied, reason, trigger }`）：

1. 前置：开关勾了、剧情模式（人格故事不渲染立绘）、说话人**在立绘列表里有立绘**
   （旁白 / 自由文本 / 立绘列表里找不到他 → `no-speaker` / `no-portrait`，跳过且不报错）；
2. 可见性用**头部（脸框）中心**是否落在取景框里判断 —— 整张立绘通常比取景框还高，逐像素框住做不到也没必要；
3. 触发条件 = 需求原文那两种：取景框里看不到说话人，**且**（背景图片宽于 16:9 **或** `zoom > 1`，
   后者即"镜头被推进"）。两个条件都不成立时（说话人本来就在画面里）不动；
4. 水平：取景中心 = 立绘矩形中心（拿不到原图尺寸时退回头部框中心）；**垂直不动**，
   只在脸已经出框时平移"刚好够用"的那一点（最小必要调整，不把人物拉到垂直中间）；
5. 最后 `clampCamera(..., 背景图片范围)`：镜头框整体留在背景里，角色在边缘时镜头就贴着背景边、不越出背景。
   背景范围 = 所有背景绘制矩形的并集（含 `posX/posY` / `scale`，与后端 `getDrawBounds` 同源）；
   拿不到背景尺寸时退回画布矩形（1920×1080），保证不会跑到画布外；
6. `zoom` 从不改（推拉始终由用户决定）；记录里已有 `to`（运镜）时，终点跟着平移同样的位移并同样夹取，
   保留用户编排的运镜幅度与时长；
7. 算出来与现有镜头差不到 1px（背景矩形取整带来的半像素）→ `unchanged`，不产生新记录对象。

**验证**：`cameraFollow.test.ts` 32 条（触发时机 / 背景范围与 16:9 判定 / 水平居中 / 贴边夹取 /
垂直最小调整 / 运镜终点平移 / 各种跳过分支）+ `RecordEditor.autoFollow.test.tsx` 4 条
（选项在「摄像机」页签里且写进工程设置、开关关着不动镜头、开关打开后移动立绘 / 切换说话人都会把镜头对过去）+
`CameraProperties.test.tsx`（勾选写回上层的开关、提示写明工程全局与手动优先）+
`projectSettings.test.ts`（默认关 / 脏值一律按关）。

### 应用内确认框 (ConfirmDialog)

**路径**: `features/common/components/ConfirmDialog/`（`askConfirm()` + `ConfirmDialogHost`，根节点 `src/index.tsx` 挂一次）

**为什么不能用 `window.confirm` / `alert`**：Electron 里它们是**主进程弹出的原生 Win32 MessageBox**
（窗口类 `#32770`），会把主进程和渲染进程一起卡住；关掉之后**窗口拿不回键盘焦点**
（实测 `document.hasFocus()` 一直是 `false`），于是所有输入框"点得着、没光标、打不了字"，
只能重启软件。用户反馈的"点完「与默认立绘裁剪一致」之后剧情编辑的「对话内容」无法输入"
就是这条：那个按钮当时用的是 `window.confirm`。

- 用法：`if (!(await askConfirm({ message, detail, confirmLabel, danger }))) return;`
- 三个选项时用 `askChoice({ message, extraLabel: "不保存", confirmLabel: "保存并新建" })`，
  结果是 `"confirm" | "extra" | "cancel"`（「新建工程」问"是否保存当前工程"就是它）
- 渲染 `role="dialog"` + `createPortal` 到 `document.body`，层级 3000（盖在任何页面/弹窗之上）；
  打开时焦点落在「确定 / 主按钮」上，Esc / 点遮罩 = 取消
- 没挂 `ConfirmDialogHost` 时（单独渲染某组件的单测）退化成原生 `window.confirm`，行为不变
  （原生对话框只能表达"是 / 否"，三选一里的"次要"按钮拿不到，按取消处理）
- **新加需要二次确认的地方一律走它**，不要再写 `window.confirm`

### 颜色面板与屏幕取色 (ColorPickerControls)

**路径**: 组件 `features/common/components/ColorPickerControls/`，纯逻辑 `features/common/utils/color.ts` / `screenColorPicker.ts`，主进程 `public/color-picker.js` + `public/color-picker-overlay.html`

剧情编辑-文本-自由文字的「文字颜色」，以及资源管理-角色编辑的「名片文字颜色 / 名片背景颜色」共用同一套颜色面板：

- **十六进制输入框**（`HexColorInput`）：接受 `#RGB` / `#RRGGBB`（`#` 可省略、大小写不限），统一规范成大写 `#RRGGBB` 再写回记录（`normalizeHexColor()`）
  - 6 位写法凑齐就立即生效；3 位简写等回车 / 失焦再提交——否则输入 `FF0000` 时前三位会被当成 `#FF0000` 提前提交
  - 非法中间值标红且不提交，失焦回退到当前生效的颜色；外部颜色变了（拖色板 / 吸管 / 切换记录）就丢弃输入草稿
  - 只放行 6 位以内：色板 `react-colorful` 不支持透明度，8 位带 alpha 的颜色存了也回显不出来
- **吸管按钮**（`ScreenColorPickerButton`）：点击后由主进程打开屏幕取色遮罩，能吸**软件窗口以外**的颜色。取色期间按钮置灰，防止连点叠出多层遮罩；取消（Esc / 右键）不回调，失败时弹提示
- 角色名片的两个颜色输入框也换成了同一个 `HexColorInput`：`FF0000` 这种不带 `#` 的写法以前会被后端判为非法格式并静默回退默认色，现在会先规范化

**屏幕取色的实现**（`public/color-picker.js`）：

1. 对每个显示器单独 `desktopCapturer.getSources()`，`thumbnailSize` 用该显示器的**物理分辨率**（`display.size × scaleFactor`）。一次调用里所有显示器共用同一个尺寸，分辨率不同的那块会被缩放插值，吸到的就不是屏幕原色
2. 截图用 PNG（`NativeImage.toDataURL()`），不能用 JPEG——有损压缩会改掉要吸的像素值
3. 每个显示器建一个无边框、`alwaysOnTop("screen-saver")` 的遮罩窗口，页面里把截图按 DIP 铺满；鼠标坐标按「截图实际尺寸 / 显示尺寸」折算回图片像素，所以 DPI 缩放不影响取色准确性
4. 遮罩页面（`color-picker-overlay.html`，`nodeIntegration` + `contextIsolation: false`，只加载本地内容）负责放大镜、色值预览、单击拾取、Esc / 右键取消
5. 所有显示器都截好、遮罩都加载完之后才统一 `show()`：一边抓一边显示的话，先显示的遮罩会被后一次截图拍进去
6. 遮罩里铺的是打开瞬间的**冻结截图**，不是实时画面：点哪个像素就取哪个像素，不受动画/视频影响
7. 遮罩加载失败、窗口被关掉、主窗口退出、超过 5 分钟都会结束会话并销毁所有遮罩；IPC 只接受本次会话自己创建的遮罩窗口发来的取色结果

**两个容易踩的坑**（改动前先看）：

- Windows 上 `new BrowserWindow({ height: 1080 })` 会被压进**工作区**（1080 高的屏幕只能拿到 1032 的窗口），截图会被纵向拉伸、遮罩也盖不住任务栏。创建后必须再 `win.setBounds(display.bounds)` 一次（`createOverlayWindow()` 里已经这么做）
- 取色结果只认 `#RRGGBB`：主进程与渲染进程各校验一次，避免别的页面伪造 IPC 消息或收到格式不对的颜色

## 构建与运行

### 开发模式

一键启动（前后端一起，需已装 Maven / JDK 21 / Node 18+）：

```bash
demo\start_all.bat
```

它做的事：`mvn spring-boot:run` 起后端 → 轮询 `http://localhost:8081/api/health` 直到通过（最多 120 秒）→ 清理占用 3000 端口的残留进程 → `npm run electron-dev` 起前端（`BROWSER=none`，只开 Electron 窗口不弹浏览器）。

手动分别启动：

```bash
# 后端（demo/ 目录）
mvn spring-boot:run

# 前端（demo/frontend/electron-react-app）
npm install
npm run electron-dev        # concurrently: CRA dev server(:3000) + wait-on 后启动 Electron
```

开发模式下 Electron **不会**自己拉起后端（`electron.js` 里 `if (!isDev)` 才启动），所以后端必须由 `start_all.bat` 或 `mvn spring-boot:run` 单独启动；后端没起来时界面仍可用，但资源与预览都会失败。

只调前端界面（不启动 Electron）也可以直接 `npm start`，浏览器打开 `http://localhost:3000`，此时走 `App.tsx`，文件读写降级为下载、日志导出按钮隐藏。

### 生产构建

```bash
# 前端产物（build/）
cd demo/frontend/electron-react-app
npm run build

# 以"安装态"本地试跑（build + electron .，不生成安装包）
npm run electron-pack

demo\build-package.bat
```

`build-package.bat` 的流程：生成内置 JRE（jlink）→ `mvn clean package -DskipTests` → `npm run build` → 停掉占用输出目录的项目进程 → `npx electron-builder --win --x64`（输出到仓库根目录 `release/`，可用 `PACK_OUTPUT` 覆盖）→ 校验打包后的 `assets/ui`、`assets/effects`、字体是否齐全（缺就直接构建失败，避免发出装完跑不起来的安装包）。

CI 走 `.github/workflows/release.yml`：校验版本号一致 → Java 21 + Node → Maven 打包 → jlink → `npm ci` + `npm run build` → `npx electron-builder --publish always`。

`electron-builder.yml` 要点：

- `asar: true`，打进 asar 的只有 `build/**/*`、`public/electron.js`、`public/preload.js`、`public/color-picker.js`、`public/color-picker-overlay.html`
- `extraResources`：后端 jar（`../../target/demo-*-SNAPSHOT.jar`）、内置 JRE、`assets`、`resources`、`data`（`project.db`、`records.json`）
- `win.executableName` 必须**无空格**：安装路径带空格时，Spring Boot 3.2 的嵌套 jar URL 会让 JavaCV/JavaCPP 解析失败，FFmpeg 原生库加载不出来，表现为"导出进度永远 0%"
- `nsis.deleteAppDataOnUninstall: true`：卸载时连用户数据目录一起删（**只删默认的** `%APPDATA%\limbus-company-plot-video-generator`；用户把数据根目录换到别的盘后，那份数据不受影响）

### 版本号

版本号唯一真源是 `demo/frontend/electron-react-app/package.json` 的 `version`，用脚本一次性同步：

```bash
node scripts/version.mjs <x.y.z> --write    # 同步到 pom.xml、package-lock.json、application.yml
node scripts/version.mjs --check            # 只校验
```

界面上的版本、安装包文件名、日志首行的版本都取自同一个值（`app.getVersion()`），所以不要在别处硬编码版本号。

### 后端生命周期

后端固定使用 **8081** 端口，安装版由主进程在 `app.whenReady()` 里拉起。以下约束是踩坑后固化的，改动前请先读：

1. **单实例守卫**：模块加载时（`whenReady` 之前）调用 `app.requestSingleInstanceLock()`，拿不到锁的实例直接 `app.quit()`，绝不启动后端。
   - 没有它时，重复双击会起两个实例、两个后端抢 8081；第二个后端启动失败后实例退出，退出逻辑会把第一个实例**健康的后端一起杀掉**，界面还开着但所有请求都失败（报"请检查后端是否正常运行"）。
   - `second-instance` 事件里把已有窗口 `restore()` + `focus()`，而不是再开一个实例。
2. **只停自己启动的后端**：后端句柄保存在 `ownedBackendProcess`，`stopBackend()` 只结束该进程；`will-quit` 里只调一次（旧实现在 `before-quit` 与 `will-quit` 各调一次，日志里会出现两条"正在停止后端"，重复 kill 同一句柄也不可靠）。
3. **`startBackend(dataRoot)` 的返回约定**（内部完成"探测端口 → 复用或启动 → 健康检查"全流程）：

   | 返回 | 含义 | 退出时是否停止后端 |
   | --- | --- | --- |
   | `{ ok: true, owned: true }` | 本实例启动并确认健康 | 是 |
   | `{ ok: true, external: true }` | 复用了其他实例已有的健康后端 | 否 |
   | `{ ok: false, reason }` | 8081 被非本应用进程占用，或启动失败 / 未通过健康检查 | — |

   `ok: false` 时主进程弹错误框并退出，不再创建窗口。该方法不会抛异常，也不会永久挂起。

4. **就绪判定必须按 PID 归属**：健康检查返回 200 只说明"8081 上有后端"，不等于"是本实例启动的后端"。`waitForBackend` 通过 `getListenerPid()`（netstat / lsof 反查监听 PID）与子进程 PID 比对，避免第二个实例把别人的后端误判成自己的。

5. **启动参数**：`java -Dapp.assets.bundled=<resources>/assets -Dlbc.data.dir=<dataRoot> -jar demo-*.jar --server.port=8081`，`cwd` 为数据根目录（`getDataRoot()`，默认即用户数据目录），`JAVA_TOOL_OPTIONS` 统一设 UTF-8 与 `Asia/Shanghai`。安装版优先用内置 JRE（`resources/jre/bin/java.exe`），没有才回退系统 `java`。
   - `-Dlbc.data.dir` 是**主进程解析出的最终值**（`--data-dir=` > `LBC_DATA_DIR` > 定位文件 > 默认），这样后端的选择优先级被主进程"覆盖"成一个确定值，两边不可能指向不同目录。

6. **首次启动准备**：`ensureUserDataFiles(dataRoot)` 把安装目录的 `data/`、`assets/`、`resources/` 复制到数据根目录（目标已存在则跳过），并确保 `logs/` 存在。这次复制只做一次，所以设置了「素材自检与修复」（`GET /api/diagnostics/assets` + `POST /api/diagnostics/assets/sync`）作为手动补齐入口。

7. **数据根目录可自定义**（设置 → 资源存储位置）：解析集中在 `public/electron.js` 顶部的「数据根目录」一节（`resolveDataRootInfo()` / `DATA_ROOT`），`getAssetsDir()`、`getLogDir()`、`ensureUserDataFiles()`、`spawnOwnBackend()` 全部只认它。定位文件 `%APPDATA%\limbus-company-plot-video-generator\data-location.json` 固定留在默认目录（否则搬到 D 盘后就找不到它了），只记录 `dataRoot` 一个字段。切换流程与安全约束：
   - 校验：不能是磁盘根目录、不能与当前目录相同、不能互相包含、必须可写；
   - 复制前先停后端并**等 8081 端口释放**（否则会复制一份写了一半的 SQLite 库）；
   - 复制 = `fs.cp` 逐个子目录，`force:false` 只补缺失文件（保留目标里已有的东西），"覆盖"时才 `force:true`；
   - 定位文件用"写 .tmp → rename"的原子写法；写失败则放弃切换并把后端按原位置重新拉起；
   - 必须重启生效（`DATA_ROOT` 在运行期是常量）；重启前也会确认后端已停止，否则新实例会"探测到已有后端就复用"，继续读旧目录；

8. **自动更新**：仅安装版启用（`electron-updater` + GitHub provider），`checkForUpdatesAndNotify()` 失败静默；有更新时通过 `update-available` / `update-downloaded` 事件通知渲染进程。主进程还注册了 `update:install`（`quitAndInstall()`），但 `preload.js` 暂未把它暴露给界面。

## 注意事项

1. **路径问题**: 开发模式页面在 `http://localhost:3000`（`window.location` 是 dev server），安装版是 `file://` 协议，两者都不能拿来当后端地址。资源 URL 一律用 `ApiService` / `AppConfig` 拼；后端地址在 `appConfig.ts`（`AppConfig.api.baseUrl`，可用 `REACT_APP_API_BASE_URL` 覆盖）和 `ApiService.ts`（`BASE_URL`，硬编码）里各有一份，改端口或换机器要**两处一起改**。
2. **CORS 与端口**: 前端 3000、后端 8081，后端已配置跨域；改端口要同时改 `appConfig.ts` / `ApiService.ts` 与后端监听端口。
3. **设计画布 ≠ 输出分辨率**: 素材坐标永远按 1920×1080 存，输出分辨率只是最终缩放。新增坐标类控件时别直接用 `videoWidth` 当坐标系。
4. **大文件与内存**: 大量图片预览注意释放 blob URL（`URL.revokeObjectURL`）；`RecordPreview` / `PortraitScenePreview` / `NamePreview` 都在替换和卸载时主动释放，新写预览组件要照做。
5. **页签切换会卸载页面组件**: 需要跨页签保留的状态必须上提到 App 层（工程数据走 `useProjectWorkspace`，设置走 `projectSettings`）。
6. **主进程 / preload 改动要重启应用**: 这两个文件不参与 HMR，改完 `electron.js` / `preload.js` 必须重启 Electron，否则会拿到旧的 `electronAPI`（代码里对缺失方法做了降级，但功能会退化）。
7. **默认立绘不要按位置判断**: 用 `defaultPortrait` 标记，`portraits[0]` 只是旧数据的兜底。
8. **情绪枚举新增要同步三处**: `types/index.ts` 的 `Emotion`、`utils/emotionMapper.ts` 的中文标签与关键词表、后端情绪枚举。目前 `Emotion.NERVOUS` 没有对应中文标签与关键词，`mapEmotion()` 会把它归一化成"正常"，下拉框里也选不出来。
9. **分组成员必须连续**: 任何调整记录顺序的新逻辑都要走 `recordGroups.ts` 的纯函数，否则"记录在数组里连续"这个不变量被破坏后，列表和播放顺序会错位。
10. **主题尚未落地**: `projectSettings.theme` 只是存了值，界面没有按它切换配色。
11. **预览几何是后端的镜像**: `preview/previewLayout.ts` 里的常量与公式（头部基准 183、身高锚点 221 + 8.333px/cm、背景 contain 缩放、0.8 场景变换 + (192,108) 偏移、对话框 / 角色名片 / 地点牌（264,826 ×1.46、-26,789 ×0.28、-2,-117 ×0.41）的位置与缩放）全部镜像自 Java 侧，**改后端渲染公式必须同步这里**；验收方式是预览舞台右下角「▦ 框」「◧ 场景」两个对位开关，以及 `previewLayout.test.ts`。
12. **预览请求要走防抖**: 预览是整图重渲染，别在 input/pointermove 里直接发请求；`RecordPreview` 已有 150ms 防抖，新增的大批量改动（拖拽、摄像机拖动）应该继续沿用"停手后提交一次"的节奏。
