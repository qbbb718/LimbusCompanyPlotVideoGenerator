# 前端架构文档

本文档描述前端应用的架构设计、组件组织和数据流。

## 技术栈

- **React 19**: UI框架（不使用组件库，均为手写组件 + CSS）
- **TypeScript**: 类型安全
- **Electron 39**: 桌面应用封装
- **Axios**: HTTP客户端
- **electron-log**: 日志记录
- **react-colorful / react-easy-crop / react-advanced-cropper**: 颜色选择与图像裁剪

## 组件架构

### 1. 剧情编辑器 (RecordEditor)

**路径**: `features/common/components/RecordEditor/`

**职责**: 提供剧情记录的完整编辑功能，包括列表展示、预览和属性编辑。

**组件层级**:
```
RecordEditor
├── RecordList              # 记录列表（下方表格）
├── RecordPreview           # 记录预览（左上方）
├── ResizablePanel          # 可调整大小的面板
└── PropertyTabs            # 属性标签页（右上方）
    ├── TextProperties      # 文本属性
    ├── CharactersProperties# 角色/立绘属性
    ├── BackgroundProperties# 背景属性
    ├── AudioProperties     # 音频属性
    └── GlobalProperties    # 全局属性
```

**数据流**:
1. 从 `ApiService.getRecords()` 加载记录列表
2. 用户选择记录 -> `selectedRecord` 状态更新
3. 属性编辑 -> 修改 `selectedRecord` -> 调用 `ApiService.updateRecord()`
4. 列表操作（增删改）-> 更新记录列表 -> 同步到后端

3. 上传文件 -> `multipart/form-data` 提交到后端

```

**文本格式**:
```

#### 日志导出 (LogExportSection)

用户的日志藏在 `%APPDATA%\limbus-company-plot-video-generator\logs`，让普通用户自己去翻不现实。
设置页提供「获取日志」按钮，点一下就能拿到一个可直接发给开发者的压缩包。

**数据流**（全程不经过后端 HTTP）：

1. 渲染进程 `window.electronAPI.exportLogs()`（`public/preload.js`）→ IPC `logs:export`
2. 主进程 `public/electron.js` 的 `logs:export` 处理器：
   - 定位日志目录：安装版 `app.getPath("userData")/logs`，开发模式 `demo/logs`
   - `collectLatestFiles()` 取最新 **10** 个文件（不足 10 个则有多少拿多少，含子目录；用 `lstat` 跳过符号链接）
   - `createZipBuffer()` 在内存里建包（`public/log-export/zip-writer.js`，deflate + CRC-32，包内目录名 `logs-<时间戳>`）
   - `dialog.showSaveDialog()` 弹保存窗口，用户选完路径再落盘（用户取消 → `{ ok:false, canceled:true }`）
3. 界面显示导出结果（文件数、压缩后体积、保存路径），用户把压缩包发给开发者

**注意**：打包和写盘都在主进程完成，渲染进程没有文件系统权限，也不该知道日志目录的绝对路径；
压缩包不依赖任何三方库（`archiver` 等只存在于 devDependencies，安装版的 app.asar 里没有），
zip 由 Node 内置 `zlib` 手工组装，这样"应用出问题时取日志"这一功能不会因为依赖缺失而失效。

## 日志系统

使用 `electron-log` 记录前端日志：
- 主进程日志: `[main:level]`
- 渲染进程日志: `[renderer:level]`
- 安装版日志目录: `%APPDATA%\limbus-company-plot-video-generator\logs`（即 `app.getPath("userData")/logs`）
- 开发模式日志目录: `demo/logs`（前端日志文件名沿用后端日志时间戳，加 `-2` 后缀）
- 后端日志（logback）也写进同一个目录，因此"取日志"时前端与后端日志能一起打包带走

用户报错时不需要自己找目录：设置页「获取日志」按钮会把该目录下最新的 10 个文件打包成 zip，
详见上方 [日志导出 (LogExportSection)](#日志导出-logexportsection)。

## 注意事项

1. **路径问题**: Electron 中需要区分开发环境和生产环境的资源路径
2. **CORS**: 开发时前端端口为3000，后端为8081，已配置跨域
3. **大文件**: 上传大图片/音频时显示加载状态，避免界面卡死
4. **内存管理**: 大量图片预览时注意释放 Blob URL

## 主进程后端生命周期（`public/electron.js`）

后端固定使用 8081 端口，由主进程在 `app.whenReady()` 里拉起。以下约束是踩坑后固化的，改动前请先读：

1. **单实例守卫**：模块加载时（`whenReady` 之前）调用 `app.requestSingleInstanceLock()`，拿不到锁的实例直接 `app.quit()`，绝不启动后端。
   - 没有它时，重复双击会起两个实例、两个后端抢 8081；第二个后端启动失败后实例退出，退出逻辑会把第一个实例**健康的后端一起杀掉**，界面还开着但所有请求都失败（报“请检查后端是否正常运行”）。
2. **只停自己启动的后端**：后端句柄保存在 `ownedBackendProcess`，`stopBackend()` 只结束该进程；`before-quit`/`will-quit` 里不再重复调用。
3. **`startBackend(userDataPath)` 的返回约定**（内部完成“探测端口 → 复用或启动 → 健康检查”全流程）：

   | 返回 | 含义 | 退出时是否停止后端 |
   | --- | --- | --- |
   | `{ ok: true, owned: true }` | 本实例启动并确认健康 | 是 |
   | `{ ok: true, external: true }` | 复用了其他实例已有的健康后端 | 否 |
   | `{ ok: false, reason }` | 8081 被非本应用进程占用，或启动失败/未通过健康检查 | — |

   `ok: false` 时主进程弹错误框并退出，不再创建窗口。该方法不会抛异常，也不会永久挂起。

4. **就绪判定必须按 PID 归属**：健康检查返回 200 只说明“8081 上有后端”，不等于“是本实例启动的后端”。`waitForBackend` 通过 `getListenerPid()`（netstat/lsof 反查监听 PID）与子进程 PID 比对，避免第二个实例误判成自己的后端。
